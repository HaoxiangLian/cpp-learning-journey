### 构建和运行

Linux、macOS 或 Git Bash：

```bash
cmake -S examples/day-33 -B build/day-33
cmake --build build/day-33
./build/day-33/robot_app
```

Windows PowerShell：

```powershell
cmake -S examples/day-33 -B build/day-33
cmake --build build/day-33
.\build\day-33\robot_app.exe
```

预期输出：

```text
clamped = 1
```

如果输出不同，先保留实际输出，不要立刻抄答案。检查编译命令、输入和第一条不同的结果。

## 第二遍：从示例推到可迁移规则

### 1. 目录不是架构，目标关系才是架构

`include/`、`src/`、`app/` 只是文件摆放；真正决定构建的是 `robot_math` 包含哪些源文件、`robot_app` 链接哪个库。现代 CMake 以 target 为中心记录这些关系。

### 2. PUBLIC、PRIVATE 在传什么

库自己的实现才需要的属性写 PRIVATE；库的公开头文件又包含并要求使用者看到的属性写 PUBLIC；只给使用者、库自身不用的写 INTERFACE。它们描述依赖传播，不是访问控制关键字。

### 3. 配置和构建分开

`cmake -S ... -B ...` 读取配置并生成构建目录；`cmake --build ...` 才执行编译链接。把生成物放在源码树外的 build 目录，能保持仓库干净并支持 Debug、Release 等不同配置。

### 4. 面试项目要可一键复现

README 应给出依赖、配置、构建、测试和运行命令。不要只上传 IDE 私有工程或本机绝对路径。面试官首先看的是能否复现，而不是目录看起来是否复杂。

## 故障实验：故意让程序出错

先不要运行，写下你认为它会在“编译、链接、运行或结果”中的哪一阶段失败。

```cpp
add_executable(robot_app app/main.cpp)
# main.cpp 包含 "robot/math.hpp"，但没有链接 robot_math，
# 因此既拿不到 PUBLIC 头文件路径，也拿不到函数定义。
```

### 根因

应先 `add_library(robot_math src/math.cpp)`，用 `target_include_directories(robot_math PUBLIC include)` 声明公开头目录，再 `target_link_libraries(robot_app PRIVATE robot_math)`。修复的是目标依赖，不是在全局随手加路径。

调试时固定按这个顺序记录：

1. 我期望看到什么？
2. 实际最早出现的不同是什么？
3. 哪条语言规则或接口契约被违反？
4. 最小修改是什么？
5. 修改后用什么输入证明问题真的修好？

## 求职面试口述

可以先照下面这段说，再换成自己的话：

> 我用 target 表达工程关系：库目标拥有源文件和公开头目录，应用目标通过 `target_link_libraries` 获取库及其 PUBLIC 使用要求。配置阶段生成构建系统，构建阶段才编译链接；构建目录与源码目录分离。

常见追问：

1. 为什么只写 `include_directories` 不如 target 级配置？
2. PUBLIC 与 PRIVATE 影响的是谁？
3. 配置阶段和构建阶段分别做什么？

合格口述不是术语数量多，而是包含“具体问题 → 代码或对象变化 → 规则 → 限制”。
