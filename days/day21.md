### 机制一：线程负责工作，`join()` 划出结果可读的边界

**实际问题**：主线程把准备数据的任务交给工作线程后，什么时候才能可靠读取结果？先看 7 行：

```cpp
int result{0};
std::thread worker{[&result] {
    result = 21;
}};

worker.join();
std::cout << result << '\n';
```

这里有 `result` 对象、`worker` 对象和两条执行流。工作线程把同一个 `result` 从 0 改为 21；主线程在 `join()` 返回后才读取。`result` 与 `worker` 离开作用域后不能再用，工作线程引用 `result` 的期间它更不能提前结束。

| 时间点 | 工作线程 | 主线程 | `result` 能否由主线程可靠读取 |
|---|---|---|---|
| 创建前 | 不存在 | 准备对象 | 可以，但仍为 0 |
| 创建后、`join` 返回前 | 可能尚未写或正在写 | 等待 | 不应并发读取 |
| `join` 返回后 | 已结束 | 继续执行 | 可以，读到 21 |

**概念落点**：这就是 [线程与 `join`（thread and join）](../docs/glossary/day21.md#线程与-jointhread-and-join)：线程是程序中可与其他执行流并发推进的一条执行流；对 `std::thread` 调用 `join()` 会等待其关联线程结束，并在成功返回后使该线程已经完成的操作先于调用线程随后的操作。

**代码与机制**：构造 `worker` 会启动一条执行流，但标准不保证它在主线程的哪一步运行。Lambda 引用外部 `result`，因此它们操作同一对象。`join()` 既等待结束，也建立工作线程操作到主线程后续操作的同步关系。可汇合的 `std::thread` 若直接析构会调用 `std::terminate`，所以每条正常路径都要明确 `join()` 或谨慎地 `detach()`；本课优先结构清楚的 `join()`。具体线程怎样映射到系统线程属于实现方式，不改变上述含义。

**错误做法与修复**：

- **未定义行为**：在 `join()` 前读取 `result`，可能与工作线程写入冲突。后果不受标准约束，不保证只是读到 0，也不保证必然崩溃。修复为先建立同步，再读取。
- **程序终止**：让仍可汇合的 `worker` 离开作用域。修复为让所有正常和异常路径在析构前完成 `join()`；更复杂代码可用管理线程生命周期的 RAII 封装。
- **悬空/未定义行为风险**：分离线程继续引用已经离开作用域的局部对象。修复为避免随意 `detach()`，把被访问对象的生命周期覆盖线程使用期。

**小检查**：若把 `std::cout << result` 移到 `join()` 前，为什么“工作线程通常很快”不能成为正确性证明？

### 机制二：共享写入必须用同一同步协议保护

**实际问题**：两个线程各执行 1000 次 `++total`，为什么最终结果不能靠“加法很简单”来保证？先看有保护的 11 行：

```cpp
int total{0};
std::mutex total_mutex;
auto add = [&] {
    for (int i{0}; i < 1000; ++i) {
        std::lock_guard<std::mutex> lock{total_mutex};
        ++total;
    }
};
std::thread first{add};
std::thread second{add};
first.join(); second.join();
```

这里只有一个 `total` 和一把 `total_mutex`，两条工作线程都引用它们。每次只有取得这同一把锁的线程能修改 `total`；两个线程结束后 `total` 为 2000。函数结束后这些对象不能再用，线程也必须在此之前结束。

| 对象 | 两个线程做什么 | 保护规则 |
|---|---|---|
| `total` | 都要读取、加一、写回 | 每次访问都持有 `total_mutex` |
| `total_mutex` | 竞争取得同一把锁 | 由 `lock_guard` 自动释放 |

**概念落点**：这就是 [数据竞争、互斥量与作用域锁（data race, mutex and scoped lock）](../docs/glossary/day21.md#数据竞争互斥量与作用域锁data-race-mutex-and-scoped-lock)：数据竞争是不同线程并发访问同一内存位置、至少一个访问是写入且这些冲突访问之间没有合适同步的情形；互斥量让同一时刻至多一个持锁线程进入受保护区域，作用域锁对象把取得和释放该锁绑定到自身生命周期。

**代码与机制**：普通 `++total` 包含读取、计算与写回，不是标准保证的跨线程原子操作。若去掉锁，两线程未同步地冲突访问同一对象，就产生数据竞争，程序行为未定义。`lock_guard` 构造时锁住 `total_mutex`，作用域结束析构并解锁；前一次解锁之前的操作对之后成功锁住同一互斥量的线程可见。锁保护的是程序员约定的临界区，不会自动寻找共享数据；所有访问者必须遵守同一协议。

**错误做法与修复**：

- **未定义行为**：两个线程直接 `++total`。结果不是简单的“可能少加几次”；标准不约束整个程序。修复为用同一互斥量保护，或在状态确实适合时使用原子操作。
- **无效保护**：每个线程各自创建一把局部互斥量。它们不会互相排斥。修复为让所有访问者引用保护该共享状态的同一同步对象。
- **可能永久等待**：手写 `lock()` 后因提前返回或异常漏掉 `unlock()`。修复为使用 `lock_guard`、`unique_lock` 或 `scoped_lock` 等作用域管理对象。

**小检查**：两个线程都只读取一个创建后不再改变的 `const int`，为什么并发只读本身不构成数据竞争？

### 机制三：多把锁必须消除循环等待

**实际问题**：转账同时需要锁住两个账户；甲按 A→B 加锁，乙按 B→A 加锁时，两边可能各拿一把再永久等待。先看安全写法 8 行：

```cpp
std::mutex left_mutex;
std::mutex right_mutex;
int completed{0};

auto transfer = [&] {
    std::scoped_lock lock{left_mutex, right_mutex};
    ++completed;
};
```

对象包括两把互斥量和计数器。进入函数的线程要协调取得两把锁后才能改变 `completed`；锁对象离开作用域时释放两把锁。所有线程结束前，这些被引用对象都必须存在。

| 危险顺序 | 线程甲 | 线程乙 | 结果 |
|---|---|---|---|
| 不一致 | 持 A，等 B | 持 B，等 A | 都无法继续 |
| 统一/协调 | 按统一策略取得 A、B | 按同一策略取得 A、B | 至少一方能完成并释放 |

**概念落点**：这就是 [死锁与锁顺序（deadlock and lock ordering）](../docs/glossary/day21.md#死锁与锁顺序deadlock-and-lock-ordering)：死锁是多个执行流各自等待只有其他等待者才能促成的条件而都无法继续的状态；固定锁顺序或让 `std::scoped_lock` 协调取得多把互斥量可以避免常见的循环等待。

**代码与机制**：C++17 的 `std::scoped_lock` 可管理一把或多把互斥量；传入多把时，它使用避免常见死锁的锁定算法，并在析构时全部释放。另一种可审查策略是规定所有代码总按同一全局顺序加锁。避免循环等待只解决这一类停滞，不自动证明共享数据保护完整，也不保证线程公平获得执行机会。

**错误做法与修复**：

- **并发活性错误**：不同路径用相反顺序取得两把锁，可能死锁，程序可能一直不再前进。修复为统一顺序或一次交给 `scoped_lock` 协调。
- **性能与活性风险**：持锁期间做慢 I/O、等待另一个任务或调用不可控回调，会扩大阻塞甚至引入新的等待环。修复为先明确不变量，尽量缩短临界区。
- **逻辑错误**：为避免死锁干脆删掉一把必要的锁，重新引入数据竞争。修复为分别验证安全性与活性，不能用一个错误替换另一个。

**小检查**：若所有代码都规定先锁账户编号较小者，再锁较大者，为什么 A↔B 两个方向也不会形成相反锁顺序？

### 机制四：原子标志发布结果，`volatile` 不承担同步

**实际问题**：生产者写好结果再把“就绪”设为真，消费者看到就绪后读取结果；仅用普通 `bool` 会再次产生竞争。先看 12 行：

```cpp
int payload{0};
int observed{0};
std::atomic<bool> ready{false};
std::thread producer{[&] {
    payload = 42;
    ready.store(true, std::memory_order_release);
}};
std::thread consumer{[&] {
    while (!ready.load(std::memory_order_acquire)) {}
    observed = payload;
}};
producer.join(); consumer.join();
```

`payload` 和 `observed` 是普通整数，`ready` 是原子布尔对象。生产者先写 `payload` 再发布；消费者获取到 `true` 后才读 `payload` 并写自己的 `observed`。两条线程都结束后才输出，相关局部对象随后离开作用域便不能再用。

| 对象 | 写入者 | 读取者 | 规则 |
|---|---|---|---|
| `ready` | 生产者 | 消费者 | 原子 release/acquire |
| `payload` | 生产者 | 消费者 | 只在发布前写、获取后读 |
| `observed` | 消费者 | 主线程 | 主线程在 `join()` 后读 |

**概念落点**：这就是 [原子操作与线程间可见性（atomic operation and inter-thread visibility）](../docs/glossary/day21.md#原子操作与线程间可见性atomic-operation-and-inter-thread-visibility)：对 `std::atomic<T>` 的单次原子操作不会被其他线程观察为中途撕裂；满足相应内存顺序的发布与获取操作还能建立同步，使发布前的写入对获取后的读取可见。

**代码与机制**：消费者的 acquire 读取若看到了生产者 release 写入的 `true`，发布前的 `payload = 42` 就先于获取后的 `observed = payload`，所以这次普通读取有可靠含义。原子标志只在所有参与者遵守协议时连接这些操作；它不会把任意代码块变成事务。忙等还会消耗执行资源，实际工程常根据等待时长选条件变量等工具。本课不要求从缓存刷新或特定 CPU 指令开始解释，因为那是实现模型，不能替代标准同步关系。

`volatile` 常被误拿来修复并发。它的准确边界是 [`volatile` 限定（volatile qualification）](../docs/glossary/day21.md#volatile-限定volatile-qualification)：`volatile` 限定用于表示对象可能受程序正常执行流之外的因素影响，并使通过相应 `volatile` 泛左值进行的访问成为实现必须保留的可观察副作用；它不建立 C++ 线程间同步。它可用于平台文档规定的设备寄存器等特殊访问，却不让 `++value` 原子，也不建立发布/获取关系。

**错误做法与修复**：

- **未定义行为**：把 `ready` 写成普通 `bool` 并由两个线程并发读写。修复为使用合适的原子协议或互斥量。
- **同步协议错误**：消费者未确认发布便读取 `payload`，或生产者先发布再写内容。修复为严格保持“写内容→release 发布→acquire 获取→读内容”。
- **概念错误**：用 `volatile bool ready` 替换原子对象。`volatile` 不提供线程同步。修复为根据单状态或复合不变量选择 `atomic` 或锁。

**小检查**：为什么 `ready` 是原子对象，不代表把任意数量的普通共享写入放到它周围都会自动安全？

## 🐛 错误代码诊断

| 现象 | 分类 | 后果边界 | 修复方向 |
|---|---|---|---|
| 两线程无同步地读写同一普通对象 | 数据竞争/未定义行为 | 标准不约束结果，不保证只是数值偶尔错误，也不保证必然崩溃 | 同一互斥协议或正确原子协议 |
| 可汇合的 `std::thread` 直接析构 | 程序终止 | 调用 `std::terminate` | 析构前 `join()`；谨慎设计分离生命周期 |
| 两线程按相反顺序取得两把锁 | 死锁风险 | 可能永久等待而不前进 | 统一顺序或 `std::scoped_lock` |
| 手写加锁后漏解锁 | 活性错误 | 后续线程可能一直阻塞 | 使用作用域锁对象 |
| 用 `volatile` 共享计数或标志 | 数据竞争/概念错误 | 不提供原子性和同步；冲突访问仍可能未定义 | 使用 `atomic`、互斥量等标准机制 |
| 复制 `std::mutex` | 编译错误 | 复制构造被删除 | 让参与者引用同一互斥量 |

### 题 1：什么是数据竞争？互斥量和作用域锁怎样保护共享数据？

**30 秒回答**：数据竞争发生在不同线程并发访问同一内存位置、至少一个是写入且冲突访问间没有合适同步时，程序行为未定义。互斥量把受保护区域排成一次只允许一个持锁线程执行；同一互斥量的解锁与随后成功加锁还建立可见性。`std::lock_guard` 用生命周期自动解锁，减少遗漏。但锁必须是同一把且覆盖共享数据的全部不变量，多把锁还要防止死锁。

**完整逻辑**：先找共享内存位置，再判断访问是否可能并发、是否含写入、是否存在同步；不要用“单核”“语句很短”或测试偶尔正确替代规则。需要保护复合状态时，用同一互斥量包住完整不变量，用 `std::lock_guard` 或 `std::scoped_lock` 管理锁生命周期。涉及多把锁时统一顺序或一次协调取得，最后区分没有数据竞争、没有死锁和业务正确是三个问题。

**可能连续追问**：

- 两个线程只读同一个对象是否需要互斥量？
- 为什么 `++count` 不能假定为原子操作？
- `std::lock_guard` 比手写 `lock()` 和 `unlock()` 好在哪里？
- 同时需要两把锁时怎样降低死锁风险？

**容易失分的说法**：把数据竞争说成“结果偶尔不对”；用单核、整数或一行代码证明线程安全；只说加锁却不指出所有线程必须遵守同一协议；把没有竞争、没有死锁和逻辑正确混为一谈。

### 题 2：`std::atomic`、互斥量和 `volatile` 有什么区别？线程间可见性怎样建立？

**30 秒回答**：`std::atomic<T>` 保证该原子对象的单次原子操作不可被观察为撕裂，并可通过内存顺序建立线程间同步；互斥量适合保护跨多个步骤或多个对象的不变量，解锁与随后成功加锁建立可见性。`volatile` 主要服务于实现规定的特殊访问，不提供原子性、互斥或线程间同步。选择取决于状态是否能用清晰的原子协议表达，而不是简单认为原子总比锁快。

**完整逻辑**：先问要保护的是单个标志/计数还是复合不变量。单个原子操作可用 `std::atomic`；多个字段必须作为整体变化时，互斥量通常更直接。再说明可见性来自明确同步关系：同一互斥量的解锁与后续加锁，或匹配的发布/获取原子操作。最后把 `volatile` 排除在线程同步工具之外，并说明性能需要测量、正确性和协议可读性优先。

**可能连续追问**：

- 原子变量周围的普通变量会自动变成原子变量吗？
- 发布/获取怎样让普通 `payload` 可见？
- 为什么 `volatile` 不能代替 `std::atomic`？
- 什么时候互斥量比原子变量更合适？
- `std::thread` 为什么通常要 `join()`？

**容易失分的说法**：把单次原子操作说成整个函数的原子事务；用缓存或 CPU 指令代替标准语义；说 `volatile` 能保证线程间可见性；不说明协议就断言普通数据一定可见。
