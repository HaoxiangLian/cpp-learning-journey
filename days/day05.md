# 第 5 天：名字何时可见，对象活多久

## 🎯 今日攻坚目标

能够分别用作用域、生命周期、存储期和链接属性解释一个名称或对象，并准确说明 `static` 在局部变量、命名空间作用域和类成员中的不同作用。

## 🔁 前置知识检查

1. 声明与定义分别为名称和实体提供什么信息？
2. 函数按值接收 `int` 时，形参与调用方对象为什么不是同一个对象？
3. 一个局部对象在花括号块结束后还能否继续通过原名称访问？“名称看不见”是否已经足以说明对象一定不存在？

## 📖 核心知识重构

今天先建立一张不会混淆的坐标系：**作用域讨论名称在源代码哪里可被找到，生命周期讨论对象在运行时何时存在，存储期讨论承载对象的存储至少可能保留多久，链接属性讨论不同声明能否指向同一实体。** `static` 会根据声明位置改变其中某一项，但它不是“以上四个概念的统称”。

### 机制一：作用域约束名称查找，内层同名声明可以隐藏外层名称

**实际问题**：传感器函数内外都出现 `reading` 时，修改内层 `reading` 会不会修改外层对象？仅凭名称拼写相同无法回答，必须先判断每个声明属于哪个作用域。

**概念落点**：直观上，花括号像给名称划出一张“可被直接叫到的地图”，但地图不是对象的寿命表。[作用域（scope）](../docs/glossary/day05.md#作用域scope)是与声明关联、决定名称在哪些程序位置能够参与名称查找的程序区域。它决定当前写下 `reading` 时能找到哪个声明，不决定相应对象采用哪种存储期，也不等于对象的生命周期。

```cpp
int reading{20};

{
    int reading{35};
    std::cout << reading << '\n';  // 找到内层声明，输出 35
}

std::cout << reading << '\n';      // 内层作用域结束，重新找到外层声明，输出 20
```

**代码与机制**：内层声明让同名外层声明在该块的剩余部分被隐藏（name hiding）。两个 `reading` 是两个对象；内层作用域结束后，外层名称重新可见，外层对象的值从未因内层赋值而改变。

作用域还包括==命名空间作用域、函数参数作用域和类作用域等==。今天先掌握块作用域与命名空间作用域；类作用域在第 8 天系统学习。编译器通常建立符号表来实现名称查找，但“必须存在某种符号表数据结构”不是 C++ 标准对生成程序的要求。

**错误做法与修复**：

```cpp
int status{1};
if (status > 0) {
    int status{2};
    status = 3;
}
std::cout << status << '\n';  // 输出 1，不是 3
```

分类：**有明确定义但结果不符合预期**。内层 `status` 隐藏了外层名称，赋值发生在内层对象上。修复不是“依赖编译器猜测”，而是避免无必要的同名声明，或明确修改外层对象而不重新声明：

```cpp
int status{1};
if (status > 0) {
    status = 3;
}
```

**小检查**：内层 `reading` 离开作用域后，外层 `reading` 是“重新创建”还是“名称重新可见”？为什么？
	名称重新可见
### 机制二：生命周期描述对象何时存在，存储期描述承载它的存储保留多久

**实际问题**：局部变量、局部 `static` 变量和动态创建对象都可能叫 `count`，但它们何时创建、何时销毁完全不同。把“出了花括号”“离开栈”“释放内存”混成一句话，会导致悬空访问和错误面试回答。

**概念落点**：

- [生命周期（lifetime）](../docs/glossary/day05.md#生命周期lifetime)是对象或引用在运行时从其初始化完成并开始存在，到被销毁或其存储被释放、重用而结束的时间区间。
- [存储期（storage duration）](../docs/glossary/day05.md#存储期storage-duration)是对象的一项属性，它规定承载该对象的存储至少可能持续多久；C++17 区分 static、thread、automatic 和 dynamic storage duration。

生命周期属于对象或引用，存储期描述承载它的存储。两者高度相关，但不是同义词：先取得大小和对齐合适的存储，再完成初始化，对象生命周期才开始；对象被销毁、存储被释放或被不相容的新对象重用时，生命周期结束。

**代码与机制**：

```cpp
void observe() {
    int sample{7};          // automatic storage duration
    static int calls{0};    // static storage duration
    ++calls;
}
```

`sample` 是普通块变量，具有自动存储期；每次执行声明都会建立并初始化本次对象，控制离开块时结束其生命周期。`calls` 具有静态存储期，其存储持续到程序结束；但这个块作用域变量的动态初始化在控制第一次经过声明时发生，因此“静态存储期”不等于“所有这类对象都在进入 `main` 前完成初始化”。

第 6 天会把自动/动态存储期与常见“栈/堆”实现模型对照。现在先记住标准层面的边界：C++ 规定存储期和对象语义，并不规定普通局部变量必须占用某个名为 stack 的物理区域，编译器也可能把无需可观察地址的值保存在寄存器中。

**错误做法与修复**：

```cpp
int& bad_reference() {
    int local{42};
    return local;  // 返回对即将结束生命周期对象的引用
}
```

分类：返回语句本身可能只收到警告；函数返回后引用成为**悬空引用**，随后通过它读取或修改对象会产生**未定义行为**。未定义行为不等于必然崩溃。当前阶段可修复为按值返回 `int`；第 6 天再完整分析引用和悬空。

**小检查**：局部 `static int calls` 的名称只在函数块内可见，为什么它的存储仍可以持续到程序结束？这说明作用域和存储期是什么关系？
	因为它有静态存储期；二者关系解耦
### 机制三：链接属性连接不同声明，`static` 在命名空间作用域限制到当前翻译单元

**实际问题**：两个 `.cpp` 文件都写下 `limit` 时，它们是同一个实体还是各自独立？“全局变量”这个口语不足以回答，因为可见范围、存储期与跨文件身份是三件事。

**概念落点**：[链接属性（linkage）](../docs/glossary/day05.md#链接属性linkage)是名称的一项属性，用来决定位于不同作用域或翻译单元中的声明能否表示同一实体。C++17 这里重点区分 external linkage、internal linkage 和 no linkage。

- ==普通命名空间作用域函数和非 `const` 变量通常具有外部链接，可由其他翻译单元中的相应声明表示同一实体。==
- ==在命名空间作用域显式写 `static` 的函数或变量名具有内部链接，只能由当前翻译单元内的声明对应到该实体。==
- ==普通块作用域局部变量名通常无链接；另一个函数里的同名局部变量不会因此成为同一对象。==

```
// ==========================================
// 地点 1：命名空间作用域（包括全局位置，或某个 namespace {} 内部）
// ==========================================
static int a = 1; // 👈 原话指的就是这个！
// 它的意思是：内部链接！这个变量 'a' 被锁死在当前 .cpp 文件里，别的源文件看不见它。


class MyClass {
// ==========================================
// 地点 2：类作用域（Class Scope）
// ==========================================
    static int b; 
    // ❌ 原话指的不是这个！
    // 写在类里面的 static 根本不是内部链接的意思。
    // 它的意思是：类的所有实例（对象）共享同一个变量 'b'。
};


void do_something() {
// ==========================================
// 地点 3：块作用域（Block Scope，也就是函数内部）
// ==========================================
    static int c = 3; 
    // ❌ 原话指的也不是这个！
    // 也就是我们上一个问题讨论的“动态初始化第一次经过时发生”。
    // 它的意思是：即使函数执行结束，变量 'c' 也不销毁，下次进来还用它。
}
```


**代码与机制**：

```cpp
static int file_limit{80};  // 名称具有 internal linkage

int public_limit{100};      // 通常具有 external linkage

void report() {
    int local_limit{60};    // 名称通常 has no linkage
}
```

三者都可以具有静态或自动存储期中的某一种，但链接属性只回答“跨声明身份”问题。`file_limit` 的静态存储期不是由“内部链接”推导出来的；命名空间作用域变量本来就具有静态存储期，`static` 在这里主要改变名称的链接属性。

现代 C++ 也常用 unnamed namespace 表达翻译单元内实体；它同样形成内部链接语义。课程仍讲命名空间作用域 `static`，因为面试与旧代码中非常常见。

**错误做法与修复**：假设 `a.cpp` 与 `b.cpp` 各自写：

```cpp
static int counter{0};
```

分类：程序可以**有明确定义但结果不符合预期**。两个名称分别具有内部链接，对应两个翻译单元各自的实体，并不是一个共享计数器。若业务确实需要一个跨文件对象，应在一个源文件中提供定义，在头文件中提供匹配的 `extern` 声明；更好的接口通常是用函数封装状态，避免暴露可修改全局变量。

**小检查**：`static int file_limit` 的“只限当前翻译单元”和“存储持续到程序结束”分别由哪个概念描述？
	内部链接；存储期
### 机制四：同一个 `static` 在三种位置改变的不是同一件事

**实际问题**：面试中只回答“`static` 让变量放到静态区”既不准确，也解释不了局部变量只初始化一次、文件内函数不可跨文件引用、类的所有对象共享一个成员这些不同现象。

**概念落点**：[static（上下文相关说明符）](../docs/glossary/day05.md#static上下文相关说明符)是在不同声明位置产生不同语言效果的关键字：==块作用域变量因此具有静态存储期，命名空间作用域名称因此具有内部链接，而类的静态成员不属于任何单个对象的普通成员子对象。==

**代码与机制**：先分别看三种位置。

1. 局部静态变量：

   ```cpp
   int next_ticket() {
       static int current{100};
       return ++current;
   }
   ```

   `current` 的作用域仍在函数体内，存储期却是静态存储期。动态初始化第一次经过声明时完成；自 C++11 起，如果多个线程并发首次进入，其他执行会等待这次初始化完成。`++current` 本身并不因此自动成为线程安全操作，并发修改留到第 21 天讨论。

2. 命名空间作用域 `static`：

   ```cpp
   static int file_limit{80};
   ```

   名称获得内部链接；不要把这层作用说成“让它活得更久”，因为命名空间作用域对象本来就具有静态存储期。

3. 类静态成员（先作语法预览，第 8 天再学习类）：

   ```cpp
   struct Registry {
       inline static int count{0};  // inline static data member，C++17
   };
   ```

   `count` 不属于每个 `Registry` 对象各自的普通成员子对象，所有对象通过同一静态数据成员观察同一值。C++17 的 `inline static` 允许在类定义中给出这个定义；非 `inline` 静态数据成员在需要定义时通常还要有类外定义。==静态成员函数也不依赖某个对象调用且没有 `this` 指针==，详细规则留到第 8 天。

**错误做法与修复**：

```cpp
struct Counter {
    static int value;  // 这里只是非 inline 静态数据成员的声明
};

int main() {
    return Counter::value;
}
```

分类：源文件通常能通过编译，但如果没有某处提供 `int Counter::value{0};`，完整程序会出现**链接错误**。修复可以提供恰当的类外定义；在 C++17 且接口设计合适时，也可写成 `inline static int value{0};`。

**小检查**：分别用“作用域、存储期、链接属性、是否属于对象子对象”说明三处 `static`，不要使用“都放在静态区”这一句概括。
	命名空间作用域中的static对象具有内部链接；
	类作用域的static类对象在类中具有唯一类静态成员，不属于类子对象；
	块作用域中的static对象具有静态存储期；
## 💻 最小可运行示例

完整代码位于 [`examples/day05/main.cpp`](../examples/day05/main.cpp)。

```cpp
#include <iostream>

static int file_limit{80};

int next_ticket() {
    static int current{100};
    return ++current;
}

struct Registry {
    inline static int registered{0};
};

int main() {
    int reading{20};
    {
        int reading{35};
        std::cout << "inner reading: " << reading << '\n';
    }

    std::cout << "outer reading: " << reading << '\n';
    std::cout << "ticket: " << next_ticket() << '\n';
    std::cout << "ticket: " << next_ticket() << '\n';

    ++Registry::registered;
    ++Registry::registered;
    std::cout << "registered: " << Registry::registered << '\n';
    std::cout << "file limit: " << file_limit << '\n';
}
```

预期输出：

```text
inner reading: 35
outer reading: 20
ticket: 101
ticket: 102
registered: 2
file limit: 80
```

观察重点：同名局部对象由作用域区分；局部静态对象跨调用保留状态；类静态成员不是每个对象一份；命名空间作用域 `static` 的核心变化是内部链接。

## 🐛 错误代码诊断

### 反例 A：非 `inline` 静态数据成员缺少定义

[`exercises/day05/broken/missing_static_definition.cpp`](../exercises/day05/broken/missing_static_definition.cpp) 被显著标记为故意错误，不进入正常构建目标。

分类：**链接错误**。类内声明让编译器知道名称和类型，但被使用的非 `inline` 静态数据成员仍缺少所需定义。

### 反例 B：把名称隐藏误判为修改外层对象

```cpp
int level{1};
{
    int level{2};
    ++level;
}
```

分类：**有明确定义但结果不符合预期**。外层 `level` 仍为 `1`；内层对象变为 `3` 后结束生命周期。

### 反例 C：返回局部对象的引用

返回发生后，局部对象生命周期已经结束，引用悬空。随后求值该引用属于**未定义行为**，但不保证崩溃、报错或输出某个固定值。

## 🎤 高频面试实战

本节保留当日主问题的答题框架。先独立口述，再到[第 5 天面试答案](../interview/answers/day05.md)逐题核对所有连续追问。

### 题 1：作用域、生命周期、存储期和链接属性有什么区别？

**30 秒口头回答**：作用域决定名称在源代码哪些位置参与名称查找；生命周期是对象或引用在运行时有效存在的时间区间；存储期决定承载对象的存储至少可能保持多久；链接属性决定不同作用域或翻译单元中的声明能否表示同一实体。它们观察的是名称、对象和存储的不同维度，不能用“都跟变量活多久有关”混为一谈。

**完整答题逻辑**：先给每个概念唯一对象：作用域与名称查找，生命周期与运行时对象，存储期与存储，链接属性与跨声明身份；再用局部 `static` 说明作用域很小但存储期很长；最后用命名空间 `static` 说明内部链接与静态存储期是两条独立结论。

**可能连续追问**：

- 名称离开作用域是否等于对象生命周期一定结束？
- 局部静态变量为什么作用域很小却能跨调用保留状态？
- 自动存储期是否由 C++ 标准保证使用机器栈？
- 块作用域普通局部变量的名称有什么链接属性？
- 命名空间作用域 `const` 变量在 C++17 中通常具有什么链接属性？

**容易失分的说法**：把作用域定义为对象存活时间；把存储期直接说成“内存区域”；声称所有局部变量必然在栈上；把链接属性说成链接器能否找到库的工程配置。

### 题 2：`static` 在局部变量、命名空间作用域和类成员中分别是什么意思？

**30 秒口头回答**：局部变量使用 `static` 后具有静态存储期，但名称仍受块作用域限制，动态初始化第一次执行到声明时完成；命名空间作用域的 `static` 让名称具有内部链接；类的静态数据成员不属于每个对象的普通成员子对象，而是类层面共享的一个实体。它们不是同一句“放进静态区”可以准确概括的。

**完整答题逻辑**：按声明位置逐项回答“改变了什么、没改变什么”：局部 `static` 改存储期不扩大作用域；命名空间 `static` 改链接属性而对象本来已有静态存储期；类静态成员改变成员与对象的归属关系。补充 C++11 局部静态初始化并发规则和 C++17 `inline static` 数据成员边界。

**可能连续追问**：

- 局部静态变量每次调用都会重新初始化吗？
- 局部静态变量的初始化线程安全吗？后续并发修改也安全吗？
- 命名空间作用域 `static` 变量能否通过 `extern` 在另一个翻译单元引用？
- 静态数据成员是否计入每个对象的 `sizeof`？
- C++17 的 `inline static` 数据成员解决了什么定义问题？

**容易失分的说法**：说三种 `static` 都只改变存储位置；把初始化线程安全扩大成所有访问都线程安全；说静态数据成员每个对象一份；忘记非 `inline` 静态数据成员可能需要类外定义。
