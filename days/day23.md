## 📖 核心知识重构

今天的“语言规则/标准语义”仍指所有符合 C++17 的实现都必须保持的代码含义；“实现方式/实现模型”仍指编译器和运行环境满足规则的具体做法。答题先依靠源代码规则，最后才补充 ABI、物理布局或性能测量。

### 机制一：先列对象、责任和有效期，再解释综合代码

**实际问题**：看到 `vector<unique_ptr<Task>>`、移动和虚函数同时出现时，很容易只喊出“智能指针”“多态”，却说不清到底有几个对象、谁负责销毁、哪个名字还能用。先看 12 行：

```cpp
struct Task {
    virtual ~Task() = default;
    virtual int run() const = 0;
};
struct Add final : Task {
    explicit Add(int value) : value_{value} {}
    int run() const override { return value_ + 1; }
    int value_;
};

auto pending = std::make_unique<Add>(4);
std::vector<std::unique_ptr<Task>> tasks;
tasks.push_back(std::move(pending));
std::cout << tasks.front()->run() << '\n';
```

普通话先说清：开始时有一个 `pending` 智能指针对象和一个 `Add` 对象；移动后，`pending` 仍存在但为空，容器里的智能指针负责那个 `Add`。调用没有改变这些对象，输出 5。容器和其中的智能指针销毁时，`Add` 才结束；空的 `pending` 不能解引用。

| 时刻 | `pending` | `tasks[0]` | `Add` 对象 | 可否调用 `run` |
|---|---|---|---|---|
| 移动前 | 负责 | 不存在 | 存在 | 经 `pending` 可以 |
| 移动后 | 存在但为空 | 负责 | 仍是同一对象 | 经 `tasks[0]` 可以 |
| `tasks` 销毁后 | 空 | 已结束 | 已结束 | 不可以 |

**概念落点**：这套按顺序记录事实的方法称为[代码辨析证据链（code-reasoning evidence chain）](../docs/glossary/day23.md#代码辨析证据链code-reasoning-evidence-chain)：代码辨析证据链是先列出对象、状态变化、管理责任和最后合法使用点，再依据已学语言规则逐步推出结论的检查方法。它是本课程的推理工具，不是 C++ 标准术语。

**代码与机制**：`make_unique` 创建 `Add` 并让 `pending` 独占管理；`std::move` 只把表达式送入可移动入口，实际的 `unique_ptr` 移动使容器元素接手责任。`tasks.front()` 得到容器中第一个智能指针，`->run()` 通过基类接口进行虚调用，因为对象实际是 `Add`，执行覆盖版本。标准保证这些可观察含义，但不规定虚调用一定使用 vtable，也不规定对象的物理地址属于口语中的“栈”或“堆”。

**错误做法与修复**：

- **未定义行为**：移动后写 `pending->run()`；空智能指针解引用不产生可依赖结果，不应说成“必然崩溃”。修复为先检查或改用当前拥有者。
- **编译错误**：复制 `unique_ptr`；它的复制操作被删除。修复为明确移动责任，或在确实需要共同管理时重新设计为 `shared_ptr`。
- **概念错误**：说“移动把 `Add` 对象搬进了 vector”。这里改变的是管理责任，被管理的 `Add` 仍是同一个对象。

**小检查**：若保存 `Task* observed = tasks.front().get();`，随后只对 `tasks` 执行 `reserve`，`observed` 是否仍指向原来的 `Add`？若随后 `tasks.clear()` 呢？

### 机制二：把结论写成条件表，避免跨机制套用绝对话

**实际问题**：面试官连续问“迭代器会不会失效”“虚函数会不会动态绑定”“加了锁是否线程安全”，单答“会”或“不会”都缺少决定答案的条件。先观察三组最小事实：

```cpp
std::vector<int> values{1, 2};
auto it = values.begin();
values.reserve(20);              // 若发生重新分配，it 失效

Base& view = derived;
view.virtual_step();              // 满足虚调用条件，选择覆盖版本

std::lock_guard<std::mutex> lock{m};
++shared_count;                   // 仅在所有冲突访问遵守同一协议时受保护
```

第一组有容器元素和迭代器，容量变化可能使旧迭代器不能再用；第二组有派生对象和引用，调用不创建第二个派生对象；第三组有共享整数、互斥量和锁对象，锁对象离开作用域后不能再用并自动解锁。三组结论都依赖代码中明确条件，不能彼此替换。

| 问题 | 先检查的条件 | 能得到的结论 | 仍不能断言 |
|---|---|---|---|
| `vector` 迭代器有效吗 | 哪种操作、是否重新分配、位置关系 | 按该容器操作规则判断 | 所有容器规则相同 |
| 会动态绑定吗 | 虚函数、引用/指针、未切片、确有覆盖 | 选择最终覆盖版本 | 标准保证 vtable 布局 |
| 共享数据安全吗 | 冲突访问是否都遵守同一同步协议 | 对该协议覆盖的访问建立保护 | 整个程序没有死锁或逻辑错误 |

**概念落点**：这张表体现[条件—结论矩阵（condition-conclusion matrix）](../docs/glossary/day23.md#条件结论矩阵condition-conclusion-matrix)：条件—结论矩阵是把一个判断所需的触发条件、在条件成立时可保证的结论以及仍未被保证的边界并排列出的分析表。它同样是课程方法，不是标准库组件。

**代码与机制**：先定位被问的具体对象，再找操作：`reserve` 影响 vector 的存储与迭代器规则；虚调用取决于静态接口与动态对象关系；互斥保护取决于所有参与线程是否使用同一把锁覆盖同一共享状态。复杂度也必须带操作、容器和平均/最坏条件。性能数据属于具体实现与输入的测量结果，不能取代标准复杂度保证。

**错误做法与修复**：

- **概念错误**：“vector 一修改，所有迭代器都失效。”修复为指出具体操作、是否重新分配以及迭代器相对修改位置。
- **概念错误**：“有 virtual 就一定多态。”修复为补上通过基类引用/指针调用、函数确为虚函数、对象未被切片等条件。
- **数据竞争风险**：“写代码时加了一把锁，所以线程安全。”若其他冲突访问绕过同一协议，仍可能发生数据竞争。修复为审计全部冲突访问和共同不变量。

**小检查**：为什么“`unordered_map` 平均查找 O(1)”不能直接推出“它一定比 `map` 快，而且引用会在 rehash 后失效”？

### 机制三：用结论、条件、依据和边界承接连续追问

**实际问题**：完整推理已经正确，但回答可能散成两分钟；只背一句结论又经不起追问。先把同一题压缩成四行：

```text
结论：移动后 source 仍是有效对象，但不再拥有原资源。
条件：这里移动的是 std::unique_ptr，移动构造成功完成。
依据：新指针接手独占责任，源指针变为空。
边界：std::move 本身不搬资源；不能把所有类型的移后状态都说成空。
```

这里有源智能指针、目标智能指针和被管理对象。目标接手责任，源变为空，被管理对象没有因此结束；源仍可检查和重新赋值，但不能解引用。四行都能回到机制一的状态表验证。

**概念落点**：这种表达称为[条件化回答（qualified answer）](../docs/glossary/day23.md#条件化回答qualified-answer)：条件化回答是先给明确结论，再说明结论成立的条件、可核对的规则依据和不能扩大到的边界的答题结构。它决定回答是否精确，不决定代码本身是否正确，也不是 C++ 关键字。

**代码与机制**：30 秒回答先给结论，防止只铺背景；条件限定讨论对象和操作；依据引用对象生命周期、所有权、容器失效或同步等已学规则；边界主动阻止“总是”“绝不”等扩大。连续追问改变一个条件时，不要推翻整段背诵，而是回到条件表重算。例如把 `unique_ptr` 改成普通类型，移后状态就只能说“有效但值未指定（若标准/类型如此规定）”，不能机械说为空。

**错误做法与修复**：

- **失分表达**：只报术语，如“这是 RAII、多态、线程安全”。修复为补对象、触发条件和可观察结果。
- **失分表达**：使用“任何、必然、全部”却不给范围。修复为加上类型、操作、生命周期或同步条件。
- **实现边界错误**：把 vtable、一次汇编结果或一次基准测试说成语言保证。修复为先给标准语义，再把实现观察标为补充。

**小检查**：把“`shared_ptr` 是线程安全的”改写成结论、条件、依据和边界四句，至少区分控制块操作与被管理对象的并发访问。

## 🐛 错误代码诊断

故意错误文件 [`exercises/day23/broken/copy_unique_tasks.cpp`](../exercises/day23/broken/copy_unique_tasks.cpp) 尝试复制装有 `unique_ptr` 的容器。

- **错误类别**：编译错误，程序非良构。
- **原因边界**：容器复制需要复制每个元素，而 `unique_ptr` 的复制构造被删除；不是“运行时可能重复释放”。
- **修复方向**：若责任应转移，移动容器；若两个调用方确需共同承担对象结束责任，再明确评估 `shared_ptr`，不能只为通过编译而替换类型。

## 🎤 高频面试实战

### 题 1：怎样分析 `vector<unique_ptr<Base>>` 中的移动、失效与多态调用？

**30 秒回答**：先分别列出容器、智能指针元素和被管理派生对象。把 `unique_ptr` 移入容器只转移独占责任，源指针仍有效但通常为空；通过容器元素取得基类指针并调用虚函数时，满足虚调用条件才执行派生覆盖版本。容器重新分配会使指向元素本身的迭代器、指针和引用失效，但通常不移动 `unique_ptr` 所管理的对象；删除元素则会结束被管理对象。最后说明虚表和物理地址都不是这些标准结论的前提。

**完整答题逻辑**：按“对象清单 → 责任变化 → 调用入口 → 容器操作 → 最后合法使用点”回答。必须区分指向 `unique_ptr` 元素的观察和通过 `get()` 指向被管理对象的观察；前者服从 vector 元素失效规则，后者还取决于被管理对象是否被销毁。多态部分只说基类接口、虚函数和实际对象，不靠 vtable 解释首要结论。

**可能连续追问**：

- `std::move` 是否亲自把派生对象搬进容器？
- vector 重新分配后，指向元素的迭代器与指向被管理对象的裸指针分别怎样？
- `tasks.clear()` 后，先前由 `get()` 得到的指针还能使用吗？
- 若基类析构函数不是虚函数，通过基类指针删除派生对象会怎样？
- 为什么把派生对象按值放进 `vector<Base>` 可能失去多态行为？

**容易失分的说法**：

- “移动后源对象没了。”
- “vector 扩容会把所有被管理对象一起搬家。”
- “只要写了 `virtual` 就一定执行派生版本。”
- “非虚析构一定导致内存泄漏。”

完整追问答案见 [Day 23 面试答案 Q045](../interview/answers/day23.md#q045)。

### 题 2：怎样把 STL、多态和并发中的绝对化说法改成可验证结论？

**30 秒回答**：先指出被问的对象与操作，再补触发条件，然后给标准保证，最后说明未保证的边界。比如 vector 失效要看具体操作和是否重新分配；动态绑定要看虚函数、基类引用或指针以及对象是否切片；线程安全要看所有冲突访问是否遵守同一同步协议。复杂度、vtable 和性能属于不同层级，不能用一次实现观察扩大成所有程序的结论。

**完整答题逻辑**：把题目写成条件—结论矩阵。对每个结论依次问：讨论哪个对象？执行了什么操作？前提是否成立？标准保证什么？实现可以怎样做但未被规定什么？怎样用最小代码或测试核对？追问只是在改变矩阵中的一格，应重新推导而不是换一句口号。

**可能连续追问**：

- “`map` 查找一定比 `unordered_map` 慢”错在哪里？
- “加了 mutex 就线程安全”还缺哪些条件？
- `shared_ptr` 的控制块并发安全是否等于被管理对象并发安全？
- “Sanitizer 没报错，所以没有未定义行为”为什么不成立？
- 面试回答中什么时候可以提 vtable、ABI 或缓存？

**容易失分的说法**：

- 只把“总是”替换成“可能”，仍不给决定条件。
- 把平均复杂度、最坏复杂度和实测耗时混成一个结论。
- 把“没有数据竞争”扩大成“没有死锁且业务正确”。
- 用实现细节替代标准规则。

完整追问答案见 [Day 23 面试答案 Q046](../interview/answers/day23.md#q046)。
