## 📖 核心知识重构

今天会同时谈语言和工具。“语言规则/标准语义”表示所有符合 C++17 的实现都要保持的代码含义；“实现方式/实现模型”表示具体编译器、构建工具和运行环境为实现这些规则采用的做法。头文件组织和单一定义规则涉及语言边界；CMake、GDB、LLDB 与 Sanitizer 是帮助我们构建和诊断的工具，不应被误说成 C++ 语法。

### 机制一：每个源文件分别形成编译输入，头文件只提供共同边界

**实际问题**：`main.cpp` 和 `reading.cpp` 都需要认识 `Reading`，但类定义重复出现会报错，函数实现重复出现在多个源文件又可能到链接阶段才失败。先看三个文件中的 12 行核心内容：

```cpp
// reading.hpp
#ifndef DAY22_READING_HPP
#define DAY22_READING_HPP
struct Reading { int id; double value; };
bool is_valid(const Reading& reading);
#endif

// reading.cpp
#include "reading.hpp"
bool is_valid(const Reading& r) { return r.id > 0; }

// main.cpp
#include "reading.hpp"
```

运行时会创建 `main` 中定义的 `Reading` 对象；头文件里的类定义只是告诉两个源文件这种对象由哪些成员组成，不会自己创建对象。`is_valid` 的函数体只在 `reading.cpp` 提供一次。局部 `Reading` 离开 `main` 的作用域后不能再用；头文件保护宏没有运行时对象和生命周期。

| 构建时刻 | `main.cpp` 看见什么 | `reading.cpp` 看见什么 |
|---|---|---|
| 处理包含后 | 类定义、函数声明、`main` | 类定义、函数声明、函数定义 |
| 分别编译后 | `main` 的编译结果及待解析调用 | `is_valid` 的编译结果 |
| 链接后 | 两边的引用与定义组合成程序 | 同左 |

**概念落点**：先理解“每个 `.cpp` 单独准备”，再理解“为什么头文件需要保护”。第一步是 [预处理与翻译单元（preprocessing and translation unit）](../docs/glossary/day22.md#预处理与翻译单元preprocessing-and-translation-unit)：预处理是正式编译前处理 `#include`、条件编译和宏等预处理指令并形成待翻译内容的阶段；一个源文件连同预处理后纳入的内容构成一个翻译单元，通常与其他翻译单元分别编译。

第二步是 [头文件保护与单一定义规则（header guard and One Definition Rule）](../docs/glossary/day22.md#头文件保护与单一定义规则header-guard-and-one-definition-rule)：头文件保护用条件预处理使同一头文件在一个翻译单元中只生效一次；单一定义规则规定实体在程序中允许出现多少个定义以及多处定义必须满足什么条件。

**代码与机制**：`#include` 在构建时把头文件内容纳入当前翻译单元，不是程序运行时读取文件。保护宏让 `reading.hpp` 即使沿不同包含路径重复到达，同一单元也只保留一次内容。普通函数在头文件声明、在一个 `.cpp` 定义，便于多个调用方共享接口而由链接阶段找到唯一实现。模板、类定义和符合条件的 `inline` 实体可以在多个翻译单元出现相同定义，但这是单一定义规则的特定许可，不是保护宏赋予的万能权限。预处理器和编译器是否生成某种中间文件属于实现方式。

**错误做法与修复**：

- **编译错误**：无保护头文件在同一翻译单元被纳入两次，类发生重定义。修复为唯一 include guard；`#pragma once` 常见但不是 C++ 标准指令。
- **链接错误/程序非良构**：把普通非 `inline` 函数定义写进被多个 `.cpp` 包含的头文件。修复为头文件保留声明、单个 `.cpp` 提供定义，或在确实满足语义时正确使用 `inline`。
- **链接错误**：声明与定义签名不一致，例如命名空间或 `const` 不同。修复为让实现包含自己的头文件，并逐项核对签名。

**小检查**：为什么 include guard 能阻止一个 `.cpp` 中重复类定义，却不能让任意普通函数定义安全地出现在很多 `.cpp` 中？

### 机制二：CMake target 把源文件、依赖和要求组织成构建图

**实际问题**：三个文件都写对了，若 `reading.cpp` 没加入可执行程序，仍会出现 `is_valid` 缺少定义。先看 7 行构建描述：

```cmake
cmake_minimum_required(VERSION 3.16)
project(day22 LANGUAGES CXX)

add_executable(day22_example main.cpp reading.cpp)
target_compile_features(day22_example PRIVATE cxx_std_17)
target_include_directories(day22_example PRIVATE .)
```

这里没有创建 C++ 运行时对象；它描述一个名为 `day22_example` 的待构建产物。两个 `.cpp` 都属于它，头文件通过包含路径找到。配置和构建结束后生成的程序才能在运行时创建前一节的 `Reading` 对象。

| 阶段 | 输入问题示例 | 常见诊断方向 |
|---|---|---|
| CMake 配置 | 源文件路径不存在、依赖包找不到 | target 与路径 |
| 编译 | 语法错误、类型不匹配、重复类定义 | 当前翻译单元首条错误 |
| 链接 | `undefined reference`、普通外部定义重复 | 目标源文件和链接依赖 |
| 运行 | 越界、悬空、错误业务结果 | 测试、调试器、Sanitizer |

**概念落点**：这就是 [CMake 目标与构建依赖图（CMake target and build dependency graph）](../docs/glossary/day22.md#cmake-目标与构建依赖图cmake-target-and-build-dependency-graph)：CMake 目标是构建系统中的命名产物及其源文件、依赖和使用要求；目标之间的依赖关系共同形成构建依赖图，CMake 据此生成具体构建工具所需规则。

**代码与机制**：`add_executable` 把两个源文件列入一个产物；`target_compile_features` 对该目标要求 C++17；`target_include_directories` 规定寻找项目头文件的位置。库目标可通过 `target_link_libraries` 建立依赖，并用 `PRIVATE`、`PUBLIC`、`INTERFACE` 控制使用要求是否传播。CMake 先配置并生成 Ninja、Makefile 或其他后端规则，真正的 C++ 检查仍由编译器完成。应优先设置 target 属性，避免全局选项无意污染其他目标。

**错误做法与修复**：

- **配置错误**：`add_executable` 写错相对路径。修复为从当前 `CMakeLists.txt` 所在目录核对路径和大小写。
- **链接错误**：漏列 `reading.cpp` 或漏链接实现库。修复为把实现加入正确 target，不能靠多写一个 `#include` 代替链接。
- **可维护性问题**：用全局 `include_directories`、`add_definitions` 把要求扩散到无关目标。修复为使用 `target_*` 命令表达最小作用范围。

**小检查**：若 `main.cpp` 能编译但最终提示 `is_valid` 未定义，为什么首先应检查 target 的源文件/库，而不是给头文件再加一遍声明？

### 机制三：调试器沿一次执行追踪“值从何时开始不对”

**实际问题**：程序能构建也不崩溃，却输出 `position: 13` 而需求是 14。只盯最后一行看不到错误在哪次更新形成。先看 7 行：

```cpp
int position{10};
const int step{2};

position += step;
position += 1;  // 本应再次加 step

std::cout << position << '\n';
```

这里只有 `position` 和 `step` 两个整数对象。第一条更新把 `position` 从 10 改为 12，第二条错误地改为 13；`step` 始终为 2。两对象离开作用域后不能再用。现在无需知道机器指令，只要在每次更新前后观察值即可找到第一次偏差。

| 暂停位置 | `position` | `step` | 与预期是否一致 |
|---|---:|---:|---|
| 初始化后 | 10 | 2 | 是 |
| 第一次更新后 | 12 | 2 | 是 |
| 第二次更新后 | 13 | 2 | 否，根因已出现 |

**概念落点**：这就是 [调试器、断点与单步执行（debugger, breakpoint and stepping）](../docs/glossary/day22.md#调试器断点与单步执行debugger-breakpoint-and-stepping)：调试器是控制并观察被调试程序执行的工具；断点让程序在指定位置暂停，单步执行让程序按源代码行或指令逐步推进，以便检查变量、调用关系和控制流。

**代码与机制**：先用能稳定复现的最小输入启动调试构建；在更新入口设断点，检查 `position` 和 `step`，逐行推进直到状态首次不符合预期。进入函数、越过函数与跳出函数是不同单步动作；调用栈帮助确认“谁调用到这里”。调试器显示的是本次具体构建和执行，优化可能折叠变量或改变逐行体验，但不会改变有定义程序应遵守的标准含义。

**错误做法与修复**：

- **排查方向错误**：只在最终输出或崩溃位置停下，就认定该行是根因。修复为反向追踪关键值，找到第一次错误写入。
- **结果不符合预期**：使用与实际问题不同的输入或构建配置，无法复现。修复为记录命令、输入、版本和环境，先建立稳定最小复现。
- **概念错误**：修改变量让程序继续后便认为问题已修复。调试器内改值只验证假设；修复必须落实到源码并重新测试。

**小检查**：程序在 `std::cout` 处显示错误值时，你应在哪些更早位置设置断点，才能区分“初始化错误”和“中途被错误修改”？

### 机制四：Sanitizer 报告执行到的受支持错误，不提供完整证明

**实际问题**：越界写入可能没有立即崩溃，最终症状还可能出现在远处。先看 6 行故意错误片段（不要放入正常示例）：

```cpp
int* values{new int[3]{1, 2, 3}};
values[3] = 9;  // 合法下标只有 0、1、2

std::cout << values[0] << '\n';
delete[] values;
values = nullptr;
```

这里有指针对象 `values` 和三个动态数组元素。第四个元素对象根本不存在，`values[3]` 不会合法修改某个数组元素，而是发生越界访问；之后即使仍输出 1，也不能证明程序有效。`delete[]` 后三个元素结束，指针被设为空后不能解引用。

| 工具 | 这类构建重点报告 | 不应据此声称 |
|---|---|---|
| ASan | 部分越界、释放后使用、重复释放、部分泄漏 | 检测所有内存或并发错误 |
| UBSan | 部分未定义行为，如部分溢出、错位访问 | 每种 UB 都能检测 |
| 普通测试 | 预期输出是否满足案例 | 覆盖所有输入和路径 |

**概念落点**：这就是 [Sanitizer 动态检测（Sanitizer dynamic checking）](../docs/glossary/day22.md#sanitizer-动态检测sanitizer-dynamic-checking)：Sanitizer 动态检测是编译器为程序加入运行时检查并在执行到可检测错误时报告诊断的工具方式；AddressSanitizer 重点检测部分内存错误，UndefinedBehaviorSanitizer 重点检测部分未定义行为。

**代码与机制**：GCC/Clang 常用 `-fsanitize=address,undefined -fno-omit-frame-pointer` 构建，再运行能触发错误的测试。插桩检查在执行到受支持问题时报告位置和调用信息；应优先修复第一处非法行为，因为后续现象可能只是连锁结果。无报告只表示本次路径没有触发工具识别的问题。数据竞争通常使用 ThreadSanitizer 等专用工具，不能说 ASan 已覆盖；不同 Sanitizer 能否组合也取决于工具说明。

**错误做法与修复**：

- **未定义行为**：访问 `values[3]`。标准不保证必然崩溃。修复为始终验证 `0 <= index && index < size`，并优先用容器表达元素数量。
- **验证不足**：只跑一个正常输入且 Sanitizer 无报告，就宣布程序无错。修复为增加边界与失败路径测试，并结合代码审查和其他工具。
- **诊断顺序错误**：忽略首个报告，只处理最后的崩溃。修复为保存完整日志，从第一处越界、悬空或未定义操作开始修复再重跑。

**小检查**：为什么“ASan 跑完无报告”最多是本次测试证据，而不是程序在所有输入下安全的证明？

## 🐛 错误代码诊断

| 现象 | 分类 | 后果边界 | 修复方向 |
|---|---|---|---|
| 头文件无保护且在同一单元重复包含类定义 | 编译错误 | 同一类被重复定义 | 添加唯一 include guard |
| 只声明函数却没把实现加入 target | 链接错误 | 调用引用找不到相应定义 | 补实现并加入源或链接库 |
| CMake 列出不存在的源文件 | 配置错误 | 无法生成有效构建规则 | 核对相对路径、大小写和版本库文件 |
| 数组三元素却访问下标 3 | 未定义行为 | 标准不约束结果，不保证必然崩溃 | 检查范围，使用容器与测试 |
| 调试器内临时改值后未修改源码 | 结果不符合预期 | 下次运行问题仍存在 | 用观察验证假设，再落实源码修复 |
| Sanitizer 无报告就认定所有路径安全 | 验证不足 | 未执行或不受支持的问题仍可能存在 | 扩充测试并组合审查/工具 |

### 题 1：头文件、源文件和 CMake target 怎样共同形成一个可执行程序？如何区分配置、编译与链接错误？

**30 秒回答**：头文件通常提供共享声明，源文件提供需要唯一实现的定义；每个 `.cpp` 连同预处理纳入的内容形成翻译单元并分别编译，链接再解析跨单元引用。CMake target 描述产物的源文件、依赖和使用要求并生成构建规则。CMake 找不到源或包是配置问题，语法/类型或重复定义出现在单个输入时多为编译问题，缺少定义或跨单元多重定义通常是链接问题。

**完整逻辑**：先从文件边界说明 `#include` 是预处理纳入而非运行时加载；再说明保护宏只避免同一翻译单元重复包含，普通外部定义仍受单一定义规则约束。随后把 CMake target 映射到源文件、库和使用要求。诊断时始终抓住第一条错误，按“配置是否生成规则→单个翻译单元能否编译→所有产物能否链接”缩小范围。

**可能连续追问**：

- 为什么头文件通常放声明，普通函数定义放在 `.cpp`？
- include guard 能解决跨翻译单元的多重定义吗？
- `target_link_libraries` 只是在最后调用链接器吗？
- 看到 `undefined reference` 应先检查什么？

**容易失分的说法**：说头文件运行时加载；把 include guard 当成全部 ODR 问题的修复；混淆配置、编译和链接阶段；只背 CMake 命令而不说明 target 关系。

### 题 2：调试器、ASan 和 UBSan 分别解决什么问题？为什么工具无报告不能证明程序正确？

**30 秒回答**：调试器让一次执行在断点暂停、单步推进并检查变量和调用关系，适合追踪状态在哪里偏离预期。ASan 通过插桩检测部分越界、释放后使用等内存错误，UBSan 检测部分未定义行为。它们都依赖实际执行路径和各自支持范围；无报告只说明本次覆盖下未发现受支持问题，不能证明未执行路径、数据竞争或业务逻辑都正确。

**完整逻辑**：先按症状选择工具：错误值用调试器追状态来源，内存越界或释放后访问用 ASan，整数溢出等受支持未定义行为用 UBSan。构建时保留调试信息和可读调用栈，运行能稳定触发问题的最小测试，从工具报告的第一处非法行为而非最终崩溃点开始修。最后用正常测试、边界测试、静态检查和并发专用工具补足动态覆盖边界。

**可能连续追问**：

- 断点停在崩溃行是否就找到了根因？
- ASan 常见能检测哪些问题？
- UBSan 报告是否表示程序必然崩溃？
- ASan 能检测 Day 21 的数据竞争吗？
- 调试构建与发布构建为什么可能表现不同？

**容易失分的说法**：把调试器说成自动修复工具；说 ASan 检测所有 UB 或数据竞争；把 UBSan 报告等同必然崩溃；无报告就宣布全部路径安全。
