字符串转传感器数值可能失败。若用 `-1` 表示失败，`-1` 也可能被误当成真实数据。错误处理的核心是让调用者无法轻易忽略“没有值”。

这句话不是本课结论，而是你要亲手验证的问题。先跑程序，再给现象命名。

## 第一遍：先跑、再沿着对象变化（必学）

```cpp
#include <iostream>
#include <optional>
#include <stdexcept>
#include <string>

std::optional<double> parse_force(const std::string& text) {
    try {
        std::size_t used = 0;
        const double value = std::stod(text, &used);
        if (used != text.size() || value < 0.0) {
            return std::nullopt;
        }
        return value;
    } catch (const std::invalid_argument&) {
        return std::nullopt;
    } catch (const std::out_of_range&) {
        return std::nullopt;
    }
}

int main() {
    for (const std::string text : {"12.5", "bad", "-2.0"}) {
        const auto force = parse_force(text);
        if (force) {
            std::cout << text << " -> " << *force << "\n";
        } else {
            std::cout << text << " -> invalid\n";
        }
    }
}
```

## 程序一步步发生了什么

| 时刻或语句 | 具体状态 | 这一步说明什么 |
|---|---|---|
| 输入 `12.5` | `stod` 成功且用完全部字符 | optional 内有 12.5 |
| 输入 `bad` | `stod` 抛 `invalid_argument` | 捕获后返回 nullopt |
| 输入 `-2.0` | 转换成功但违反业务范围 | 返回 nullopt |
| 调用者 `if (force)` | 显式区分有值与无值 | 只有有值时才能解引用 |

## 第二遍：从示例推到可迁移规则

### 1. 先给失败分类，再选工具

用户输入不合法通常是可恢复错误；程序内部索引越界可能是 bug；文件打不开要带上下文向上传递。返回值、optional、异常和断言各自适合不同失败，不能用一种机制包办。

### 2. optional 解决的是有或无

`optional<T>` 不解释失败原因，只把“可能没有 T”编码进类型。调用者需要先检查再取值。若业务还需要错误码或详细消息，应使用结果结构体或 C++23 `expected`；本课程按 C++17 不假装已有 `std::expected`。

### 3. 异常传播时 RAII 为什么重要

异常会跳过普通返回路径，但已成功构造的局部对象仍会析构，这叫栈展开。若资源由 vector、string、智能指针和文件流管理，清理仍能发生；裸 `new` 后尚未交给 RAII 对象则容易泄漏。

### 4. 不要捕获后什么都不做

空的 `catch (...) {}` 会抹掉故障证据。能在当前层补救才捕获；否则补充上下文后继续传播，或让上层统一处理。异常不是正常分支的替代品。

## 故障实验：故意让程序出错

先不要运行，写下你认为它会在“编译、链接、运行或结果”中的哪一阶段失败。

```cpp
double parse_force(const std::string& text) {
    try {
        return std::stod(text);
    } catch (...) {
        return -1.0;
    }
}

// 调用者把 -1.0 直接加入平均值，失败数据混入真实数据。
```

### 根因

哨兵值 `-1.0` 依赖所有调用者记住隐藏约定，而且合法值域一变就可能冲突。用 `optional<double>` 让“无值”成为类型的一部分；若要解释原因，则返回包含值或错误信息的结果类型。

## 求职面试口述

可以先照下面这段说，再换成自己的话：

> 我先区分错误类别：可预期的无值可用 optional，需携带原因可用结果对象，跨多层且当前层无法处理的失败可考虑异常，程序内部不变量用断言。异常传播期间会栈展开，因此资源应由 RAII 对象持有。

常见追问：

1. optional 为什么不能代替所有错误类型？
2. 异常传播时哪些对象会析构？
3. 什么情况下断言不应替代运行时错误处理？

合格口述不是术语数量多，而是包含“具体问题 → 代码或对象变化 → 规则 → 限制”。
