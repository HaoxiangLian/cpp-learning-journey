## 第一遍：先跑、再沿着对象变化（必学）

```cpp
#include <cmath>
#include <iostream>
#include <stdexcept>
#include <string>

double clamp_position(double value, double low, double high) {
    if (low > high) {
        throw std::invalid_argument("low must not exceed high");
    }
    if (value < low) {
        return low;
    }
    if (value > high) {
        return high;
    }
    return value;
}

void expect_near(double actual, double expected, const std::string& name) {
    if (std::fabs(actual - expected) > 1e-9) {
        throw std::runtime_error(name + " failed");
    }
    std::cout << "[PASS] " << name << "\n";
}

int main() {
    expect_near(clamp_position(0.2, -1.0, 1.0), 0.2, "inside");
    expect_near(clamp_position(-2.0, -1.0, 1.0), -1.0, "below");
    expect_near(clamp_position(2.0, -1.0, 1.0), 1.0, "above");
    expect_near(clamp_position(1.0, -1.0, 1.0), 1.0, "boundary");
}
```

## 程序一步步发生了什么

| 时刻或语句 | 具体状态 | 这一步说明什么 |
|---|---|---|
| `inside` | 走最后一个 return | 验证正常区间 |
| `below` | 命中 `value < low` | 验证下界裁剪 |
| `above` | 命中 `value > high` | 验证上界裁剪 |
| `boundary` | 等于 high，不属于越界 | 直接返回 1.0 |
| 任一不一致 | `expect_near` 抛异常 | 进程非成功结束，CI 可检测 |

现在再读后面的术语，它们只是给上表中已经发生的事情命名。

## 第二遍：从示例推到可迁移规则

### 1. 测试从需求导出，不从实现抄写

需求说输出必须落在 `[low, high]`，测试就覆盖区间内、低于、等于边界、高于以及非法 low/high。若测试只是重复实现分支，很可能把同一个误解写两遍。

### 2. 浮点数不要默认直接相等

经过计算的浮点结果可能存在舍入误差，因此示例用容差比较。容差也不能随便写一个巨大数字；要结合数值尺度和业务允许误差。对精确赋值的简单场景，直接相等有时仍合理。

### 3. 动态测试、静态分析和警告互补

测试只覆盖实际运行到的路径；编译器警告和静态分析可以发现未运行路径的可疑代码，但也不能证明业务结果。求职项目至少启用严格警告，并把测试接入 CMake/CTest 或 CI。

### 4. 代码审查看证据

好的 PR 说明改了什么、为什么、如何测试、还存在哪些限制。审查者关注接口契约、资源所有权、边界和故障路径，不是只看格式。

## 故障实验：故意让程序出错

先不要运行，写下你认为它会在“编译、链接、运行或结果”中的哪一阶段失败。

```cpp
double clamp_position(double value, double low, double high) {
    if (value < low) {
        return high;  // 写反了
    }
    if (value > high) {
        return high;
    }
    return value;
}

// 只测 clamp_position(0.2, -1, 1)，仍会通过。
```

### 根因

仅有正常区间测试不会执行错误分支。加入 `value < low` 的边界类用例后，期望 -1.0、实际得到 1.0，故障立即暴露。这说明覆盖业务分区比追求“有测试文件”重要。

调试时固定按这个顺序记录：

1. 我期望看到什么？
2. 实际最早出现的不同是什么？
3. 哪条语言规则或接口契约被违反？
4. 最小修改是什么？
5. 修改后用什么输入证明问题真的修好？

## 求职面试口述

可以先照下面这段说，再换成自己的话：

> 我从接口契约划分等价类和边界值，自动检查正常与失败路径；浮点结果按业务容差比较。测试、严格警告、Sanitizer 和静态分析互补，PR 中会给出可复现的验证命令与剩余限制。

常见追问：

1. 为什么只有 happy path 的测试价值有限？
2. 浮点容差应该依据什么选择？
3. 静态分析与运行测试各自看不到什么？

合格口述不是术语数量多，而是包含“具体问题 → 代码或对象变化 → 规则 → 限制”。
