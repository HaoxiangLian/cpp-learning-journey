## 📖 核心知识重构

今天仍以 C++17 的语言规则为准：它们是所有符合该标准的实现都必须保持的代码含义。编译器、操作系统和 ABI 怎样实现这些含义属于第二遍补充，不承担今天的首要判断。

### 机制一：模拟笔试先定位失败阶段，再追踪对象状态

**实际问题**：综合题常把编译错误、对象移动和生命周期放在一起。若一看到 `std::move` 就写“对象被销毁”，后续判断都会偏离。先限时读下面 10 行：

```cpp
std::vector<std::unique_ptr<int>> values;
auto owner = std::make_unique<int>(7);
values.push_back(std::move(owner));

if (!owner) {
    std::cout << *values.front() << '\n';
}

values.clear();
// std::cout << *values.front();
```

这里有一个 `owner` 智能指针对象、一个 vector、vector 中后来创建的智能指针元素，以及一个值为 7 的 `int` 对象。移动后 `owner` 变为空，容器元素接手管理责任，`int` 没有被销毁；程序输出 7。`clear()` 后元素和 `int` 都结束，不能再调用 `front()`，更不能解引用其结果。

| 时刻 | `owner` | `values[0]` | `int` 对象 | 合法观察 |
|---|---|---|---|---|
| 移动前 | 负责 | 不存在 | 存在 | `*owner` |
| 移动后 | 空但仍可赋值 | 负责 | 存在 | `*values.front()` |
| `clear` 后 | 空 | 已结束 | 已结束 | 只能检查容器为空 |

**概念落点**：今天用[综合验收（integrated assessment）](../docs/glossary/day24.md#综合验收integrated-assessment)组织这次检查：综合验收是用同一组限时任务同时检查代码能否构建运行、对象状态能否预测、错误能否分类以及结论能否说明条件与边界的验证过程。依赖顺序是“失败阶段 → 对象清单 → 状态变化 → 最后合法使用点 → 标准边界”。

**代码与机制**：前两行创建容器、智能指针和被管理对象；`push_back` 选中 `unique_ptr` 的移动构造，改变的是管理责任。`if (!owner)` 可安全检查移后源指针；`front()` 只在容器非空时有前置条件。注释行若执行，不是“必然崩溃”，而是先违反 `front()` 的前置条件，程序行为没有可依赖结果。模拟笔试应先判断代码是否良构，再沿执行顺序记录对象，最后才写输出和风险。

**错误做法与修复**：

- **概念错误**：说“`std::move` 销毁了 `owner`”。修复为区分仍存在的源指针对象、被转移的责任和仍存活的 `int`。
- **未定义行为风险**：在空 vector 上调用 `front()`。后果不是标准保证的崩溃；修复为先检查 `empty()`，并重新确定最后合法使用点。
- **答题错误**：只写最终输出，不说明注释行为何不能启用。修复为同时写阶段、对象、状态和边界。

**小检查**：若在 `clear()` 前保存 `int* observed = values.front().get();`，它在 `clear()` 前后分别能否解引用？

### 机制二：模拟面试让每个结论都能回到证据

**实际问题**：知道知识点不等于能应对追问。面试官把一个条件改掉时，背诵答案会断裂；条件化回答则能重新计算。先把一次回答写成 8 行：

```text
结论：这里会调用派生类的 run。
条件：经 Base& 调用虚函数，实际对象是 Derived，且签名正确覆盖。
依据：虚调用按最终覆盖版本选择行为。
边界：标准保证调用结果，不保证用 vtable 实现。

追问：若按值传给 Base 呢？
重算：派生部分被切掉，目标 Base 对象不再是原派生对象。
结论：不能沿用刚才的动态对象条件。
```

这里有原派生对象、引用或按值形参对象。引用调用不复制对象；按值传递会初始化一个独立的 `Base` 对象。引用离开作用域后不能再用，但不会因此销毁仍存活的原对象；按值形参在函数返回时结束。

**概念落点**：继续使用 Day 23 的[条件化回答](../docs/glossary/day23.md#条件化回答qualified-answer)和[代码辨析证据链](../docs/glossary/day23.md#代码辨析证据链code-reasoning-evidence-chain)。今天不创造新的 C++ 规则，而是把两种方法放进 10 分钟计时：先给结论，再在追问改变条件时回到对象和规则重新推导。

**代码与机制**：第一轮条件包括虚函数、基类引用和实际派生对象；第二轮把“引用”改成“按值对象”，因此对象清单已经变化，不能只替换一句话。完整回答应明确标准保证的调用含义，同时把 vtable 标为常见实现方式。面试录音复盘时，逐句标记“结论、条件、依据、边界”，缺一项就回到最小代码补证据。

**错误做法与修复**：

- **失分表达**：“有 `virtual` 就一定多态。”修复为补齐调用入口、实际对象和覆盖条件。
- **失分表达**：“按值传递只是复制一个指针。”修复为列出新创建的 `Base` 形参对象及其结束时间。
- **实现边界错误**：用 vtable 地址解释标准为何必须动态选择。修复为先说可观察调用语义，再把实现模型作为可删除的补充。

**小检查**：若把 `Base&` 改为 `Base*` 且指针为空，哪一项条件变化了？为什么不能继续声称会调用派生版本？

### 机制三：最小闭环项目把输入、责任、行为和验证连起来

**实际问题**：零散练习都能做对，仍可能不会组织一个小程序。先看任务队列的最小主流程：

```cpp
SensorQueue queue;
queue.push(std::make_unique<AverageTask>("room", 20, 24));
queue.push(std::make_unique<ThresholdTask>("motor", 91, 80));

for (const Result& result : queue.run_all()) {
    std::cout << result.name << ": "
              << result.value << '\n';
}
```

这里有一个队列对象、两个派生任务对象、两个临时智能指针和返回的结果容器。`push` 后临时指针的责任移入队列；`run_all` 读取任务并创建独立结果，不改变任务责任。队列销毁后任务不能再用，返回结果仍可独立存在。

| 步骤 | 任务由谁管理 | 谁发生变化 | 此后不能再用什么 |
|---|---|---|---|
| `make_unique` 后 | 临时智能指针 | 创建任务 | 无 |
| `push` 后 | 队列元素 | 责任转移 | 不能解引用移后临时指针 |
| `run_all` 后 | 仍是队列元素 | 新建结果容器 | 无 |
| 队列销毁后 | 无 | 任务结束 | 任务的指针或引用 |

**概念落点**：这个范围称为[最小闭环项目（minimum closed-loop project）](../docs/glossary/day24.md#最小闭环项目minimum-closed-loop-project)：最小闭环项目是能独立完成输入建模、状态约束、核心处理、结果输出和自动验证的一小组可构建代码。它不是“代码越少越好”，而是每项需求都有可观察结果，每个管理责任都有结束点。

**代码与机制**：抽象 `Task` 定义稳定接口并提供虚析构；派生任务用构造函数建立有效状态；`vector<unique_ptr<Task>>` 表达队列独占任务；`push` 转移责任；`run_all` 通过基类接口调用覆盖版本并返回值对象。`examples/day24/main.cpp` 是完整 C++17 实现。项目验收同时运行普通构建、预期输出和 ASan/UBSan；工具无报告只说明本次覆盖未发现受支持错误，不是程序绝对正确的证明。

**错误做法与修复**：

- **编译错误**：复制含 `unique_ptr` 的队列。修复为移动明确转交责任，或重新设计接口；不要为通过编译随意改成共享拥有。
- **设计错误**：队列保存裸指针却不说明谁销毁任务。修复为用 `unique_ptr` 把独占责任写进类型。
- **验证错误**：只在一个编译器上“运行没崩”就宣布完成。修复为检查警告、输出、故意失败阶段和动态检测边界。

**小检查**：为什么 `run_all()` 返回 `vector<Result>` 后，即使队列随后销毁，调用方仍可读取结果？

### 机制四：把错因变成 2/7/14/30 天复习动作

**实际问题**：课程结束后从 Day 01 顺序重读，容易把时间花在已经会的内容上，却让真实错因继续存在。先把本次验收记录成四个时点：

| 时间 | 输入 | 动作 | 通过证据 |
|---|---|---|---|
| +2 天 | 本次错题与录音 | 不看答案重做、重答 | 能指出原误判条件 |
| +7 天 | 三个薄弱机制 | 各写最小代码并运行 | 输出和对象表一致 |
| +14 天 | 任务队列新需求 | 改动一种任务或错误路径 | 构建、测试、Sanitizer 通过 |
| +30 天 | 全套随机题 | 再做一次限时综合验收 | 与本次结果可比较 |

复习时仍是题目、代码对象、记录表和学习者本人四类信息。每次变化的是答案质量、错误分类和代码；旧记录作为比较依据继续可用，不应被覆盖到无法追踪。

**概念落点**：[间隔复习（spaced review）](../docs/glossary/day24.md#间隔复习spaced-review)是把同一知识在逐渐拉开的时间点主动提取并依据错因调整下一次练习的学习安排。这里的关键不是按日历被动重读，而是不看答案先输出，再以证据更新薄弱项。

**代码与机制**：+2 天修正刚暴露的错误；+7 天用最小代码验证记忆；+14 天通过改需求检查能否迁移；+30 天重新限时验收。把错因写成“遗漏了哪个条件、混淆了哪两个对象、误判了哪个阶段”，比只记“粗心”更可执行。复习安排是学习方法，不是 C++ 标准语义，也不保证只按四次练习就永久掌握。

**错误做法与修复**：

- **复习策略错误**：按页数重读但不先作答。修复为先闭卷预测输出、对象状态或 30 秒回答。
- **记录错误**：只记分数，不记错因。修复为分类到阶段、对象、规则条件或表达边界。
- **计划错误**：所有知识平均分配时间。修复为让下一轮任务由最新错因驱动，同时保留少量随机抽查。

**小检查**：若 +7 天仍把“移动源对象”说成“已经销毁”，+14 天任务应怎样改，才能直接暴露并纠正这个误解？

## 🐛 错误代码诊断

故意错误文件 [`exercises/day24/broken/copy_sensor_queue.cpp`](../exercises/day24/broken/copy_sensor_queue.cpp) 尝试复制内部保存 `unique_ptr` 的队列。

- **错误类别**：编译错误，程序非良构。
- **原因边界**：复制 vector 需要复制元素，而 `unique_ptr` 的复制构造被删除；这不是一个“运行时可能失败”的操作。
- **修复方向**：需要转交整批任务时移动队列；只需读取时传引用；只有业务确实要求共同管理时才重新设计共享关系。

## 🎤 高频面试实战

### 题 1：请设计一个传感器任务队列，并说明对象、所有权、多态和异常边界

**30 秒回答**：我会让抽象 `Task` 提供虚析构和执行接口，由具体任务构造时建立有效状态；队列使用 `vector<unique_ptr<Task>>` 独占管理任务，`push` 明确移动责任，执行时通过基类接口动态调用并返回独立结果。要分别说明移后源指针、容器元素和任务对象的有效期。若任务可能失败，还要规定逐项继续还是整体停止，以及队列状态提供哪一级异常安全保证；虚表布局不是设计成立的前提。

**完整答题逻辑**：先列需求和不变量，再列对象及管理责任；选择抽象接口与派生实现；把所有权写入容器元素类型；说明 `push`、执行和销毁的状态变化；最后列构建、输出、故意错误和 Sanitizer 验证。扩展并发时必须重新定义共享状态和同步协议，不能因为容器使用智能指针就宣称线程安全。

**可能连续追问**：

- 为什么队列选择 `unique_ptr<Task>`，而不是 `Task`、裸指针或默认使用 `shared_ptr<Task>`？
- 把一个任务移入队列后，源智能指针和任务对象分别是什么状态？
- `run_all()` 返回值为什么可以在队列销毁后继续使用？
- 若某个任务执行时抛异常，怎样定义并实现可说明的失败策略？
- 若多个线程同时提交和执行任务，需要补充哪些同步条件？

**容易失分的说法**：

- “智能指针天然让整个队列线程安全。”
- “移动后源对象已经不存在。”
- “异常一定会让队列回到调用前状态。”
- “多态就是对象里一定有一张虚函数表。”

完整追问答案见 [Day 24 面试答案 Q047](../interview/answers/day24.md#q047)。

### 题 2：怎样证明 24 天学习后已经形成 C++ 知识骨架，并安排后续复习？

**30 秒回答**：不用“看完了”证明掌握，而用同一套综合任务检查四项证据：代码能否独立构建运行，对象和责任能否逐步预测，错误能否按阶段分类，结论能否说明条件和边界。记录具体错因后，在 +2 天闭卷纠错、+7 天重写最小例、+14 天修改综合项目、+30 天重新限时验收。每轮根据新错因调整，而不是平均重读全部内容。

**完整答题逻辑**：先固定一套可比较的验收标准，再保存输出、对象表、错误分类和口述记录。失败项必须定位到某条规则或某个缺失条件。复习采用主动提取和逐渐拉开的时间点；项目改动负责检查迁移能力，随机题负责防止只记住原题。工具通过和分数只是证据的一部分，不能替代对未覆盖路径与标准边界的说明。

**可能连续追问**：

- 为什么“所有示例都运行成功”仍不能单独证明已经掌握？
- +2、+7、+14、+30 天四次复习各自应该解决什么问题？
- 怎样把“粗心”改写成下一次可执行的错因记录？
- 若 +14 天项目测试通过，但仍说不清对象何时失效，是否算通过？
- 30 天后仍反复错同一类题，怎样调整路线而不是从头重读？

**容易失分的说法**：

- “把 24 篇讲义再看一遍就行。”
- “Sanitizer 没报错证明程序没有未定义行为。”
- “只要面试答案背得完整，就能处理条件变化。”
- “复习日期到了，无论会不会都做同样内容。”

完整追问答案见 [Day 24 面试答案 Q048](../interview/answers/day24.md#q048)。
