## 📚 今日术语卡

### 对象（object）与变量（variable）

直观模型：对象是程序运行时实际存在、可以保存状态的实体；变量是代码用来找到具名对象或具名引用的名称入口。

正式定义和边界见[术语表：对象](../docs/glossary.md#对象object)与[术语表：变量](../docs/glossary.md#变量variable)。今天的示例都让变量指向普通对象；引用在第 6 天展开。

### 值（value）与类型（type）

直观模型：值是对象当前表示的信息，类型是解释这份信息并约束合法操作的规则。

正式定义和边界见[术语表：值](../docs/glossary.md#值value)与[术语表：类型](../docs/glossary.md#类型type)。类型不只是“占多少字节”；C++ 也没有保证所有实现的 `int` 都恰好是 4 字节。

### 初始化（initialization）

直观模型：对象第一次出现时就要建立一个初始状态。

正式定义见[术语表：初始化](../docs/glossary.md#初始化initialization)。`int count = 0;` 虽然含有 `=`，但整个声明仍然是在初始化对象。

### 赋值（assignment）

直观模型：对象已经存在，再把它当前表示的值改成另一个值。

正式定义见[术语表：赋值](../docs/glossary.md#赋值assignment)。赋值不会重新创建同一个对象。

### `const` 限定（const qualification）

直观模型：对象建立初始状态后，不允许通过该对象的普通访问方式再次修改。

正式定义见[术语表：const 限定](../docs/glossary.md#const-限定const-qualification)。`const` 不自动意味着值在编译期已知，也不保证对象一定放在硬件只读区。

## 📖 核心知识重构

### 机制一：对象、变量、值和类型分别回答不同问题

1. **实际问题**：一个传感器程序需要表示设备编号、采样次数和温度。如果把它们都叫“一个数”，代码容易错误地混用状态。
2. **定义与设计取舍**：对象回答“运行时哪个实体保存状态”，变量回答“代码用什么名称访问它”，值回答“当前表示什么信息”，类型回答“哪些值和操作合法”。拆开这些概念会增加几个术语，却能让后续的指针、引用、生命周期和类对象建立在同一模型上。
3. **底层机制**：对象占据存储，类型规定如何解释对象的表示并约束操作。具体使用寄存器、栈地址还是其他实现方式由编译器和运行环境决定；C++ 标准不要求每个变量都必须对应一个可观察的固定内存地址。
4. **错误做法与后果**：用 `int` 表示需要小数的温度，之后把 `21.75` 变成整数，会丢失小数信息。若转换结果在目标类型可表示范围内，这通常是**有明确定义但结果不符合预期**，而不是编译器一定报错。修复是先选择能表达需求的类型，例如 `double`。

```cpp
const int sensor_id{12};          // 变量 sensor_id 指向一个 const int 对象，值为 12
int sample_count{0};              // int 对象，值为 0
double temperature_celsius{21.75}; // double 对象，值为 21.75
```

今天只使用几个常见基本类型：

| 类型 | 适合表达 | 重要边界 |
|---|---|---|
| `int` | 有正负的整数计数或编号 | 精确位数与最大范围由实现决定，但标准规定最低范围 |
| `double` | 含小数的近似数值 | 浮点值通常是近似表示，不保证任意十进制小数都精确 |
| `bool` | `true` 或 `false` 状态 | 表达逻辑状态，不应用作多种业务状态的编号 |

### 机制二：初始化发生在创建时，赋值发生在创建后

1. **实际问题**：传感器采样次数必须从已知状态开始。如果对象先存在但值未知，第一次读取就无法可靠推理。
2. **定义与设计取舍**：初始化负责建立初始状态；赋值修改已存在对象。推荐在声明位置直接初始化，并在不需要延后决定状态时使用花括号形式。
3. **底层机制**：初始化由声明选择相应初始化规则；赋值则对已建立的对象执行赋值操作。对于今天的基本类型，看起来都像“放入一个值”，但语言阶段不同；类对象在第 9—10 天会体现更明显的差异。
4. **错误做法与后果**：函数体内的 `int sample_count;` 没有给基本类型对象确定初值，直接读取其不确定值会触发**未定义行为**。标准不保证它是 0，也不保证一定崩溃。修复为 `int sample_count{0};`。

常见形式：

```cpp
int first_count{0};   // 列表初始化：推荐的清晰形式
int second_count = 0; // 这里仍是初始化，不是赋值
int third_count(0);   // 直接初始化

first_count = 1;      // 对已经存在的对象赋值
```

花括号初始化会拒绝许多可能丢失信息的窄化转换：

```cpp
int temperature{21.75};  // 故意错误：编译错误，列表初始化拒绝窄化
```

正确修复不是“想办法压掉错误”，而是根据需求选择类型：

```cpp
double temperature{21.75};
```

### 机制三：`const` 表达初始化后不再修改的约束

1. **实际问题**：一次运行中，传感器编号或最大采样数不应被后续代码意外修改。只靠注释无法让编译器帮助检查。
2. **定义与设计取舍**：给对象的类型添加 `const` 限定，让普通修改表达式成为编译错误。代价是对象必须在创建时得到可用初始状态，后续也不能把“本来应该变化的状态”误设为 `const`。
3. **底层机制**：`const` 是类型系统约束。编译器可以利用不允许普通修改这一事实进行检查和优化，但标准没有规定对象必须位于某块硬件只读内存。
4. **错误做法与后果**：定义 `const int sensor_id{12};` 后执行 `sensor_id = 13;`，属于**编译错误**。修复要先判断需求：编号确实固定就删除错误赋值；编号需要变化就不应把该对象设计为 `const`。

`const` 不等于“编译期已知”。下面的 `runtime_sensor_id()` 在程序运行时才被调用，但其结果仍可初始化一个之后不再修改的对象：

```cpp
int runtime_sensor_id() {
    return 12;
}

const int sensor_id{runtime_sensor_id()};
```

编译期求值属于另一套规则，第 3 天只做必要引入，后续会继续巩固。

## 💻 最小可运行示例

完整代码位于 [`examples/day02/main.cpp`](../examples/day02/main.cpp)。

```cpp
#include <iostream>

int main() {
    const int sensor_id{3};
    int sample_count{0};
    double temperature_celsius{21.75};

    std::cout << "sensor: " << sensor_id << '\n';
    std::cout << "sample " << sample_count << ": "
              << temperature_celsius << " C\n";

    sample_count = 1;
    temperature_celsius = 22.125;

    std::cout << "sample " << sample_count << ": "
              << temperature_celsius << " C\n";
    return 0;
}
```

预期输出：

```text
sensor: 3
sample 0: 21.75 C
sample 1: 22.125 C
```

观察重点：三个对象都在声明时初始化；之后只给两个非 `const` 对象赋值；`sensor_id` 保持不变。

## 🎤 高频面试实战

### 题 1：初始化和赋值有什么区别？为什么推荐列表初始化？

**30 秒口头回答**：初始化在对象创建时建立初始状态，赋值是在对象已经初始化之后修改当前状态。`int count = 0;` 虽然有等号，仍然是初始化。花括号初始化表达清晰，并会拒绝很多窄化转换，例如 `int value{3.5}` 是编译错误；但它不是所有类型问题的万能检查器。

**完整答题逻辑**：先按发生时机区分，再比较最小代码，最后说明列表初始化的价值和边界。对于基本类型，二者表面都像写入值；对于类类型，它们可能分别选择构造和赋值操作，后续课程展开。

**可能连续追问**：

- `int x = 1;` 中的 `=` 为什么不是赋值？
- `int x;` 是否一定初始化为 0？
- 花括号为什么会拒绝 `int x{3.5};`？
- 初始化与赋值对类对象可能有什么不同？

**容易失分的说法**：根据是否出现 `=` 判断赋值；断言所有未显式初始化的整数都是 0；声称花括号能够阻止一切精度问题。

### 题 2：`const` 对象一定是编译期常量吗？

**30 秒口头回答**：不一定。`const` 的核心含义是不能通过相应对象的普通访问方式修改它；初始化值可以在运行时得到。因此“初始化后不可普通修改”和“编译期可求值”是两个不同问题。具体编译期常量规则需要结合表达式和语言版本判断。

**完整答题逻辑**：先给出 `const` 的修改约束，再举 `const int id{runtime_sensor_id()};`，说明函数结果可在运行时产生；最后强调 `const` 也不保证某种物理存储位置。

**可能连续追问**：

- `const` 对象为什么通常必须初始化？
- `const` 是否意味着一定放在只读段？
- `const` 与编译期求值概念有什么区别？
- 指针上的 `const` 有哪些位置差异？

最后一个追问会在第 6 天结合指针正式回答。

**容易失分的说法**：把 `const` 等同于宏；声称所有 `const` 值都在编译期确定；声称它们一定存放在只读内存。
