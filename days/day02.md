## 📖 核心知识重构

不要把“对象、变量、值、类型”当作四个互不相干的名词。先观察同一组传感器状态在代码中怎样出现，再逐层回答：运行时有什么、代码怎样称呼它、它当前表达什么、哪些操作被允许。

### 机制一：用一行声明串起对象、变量、值和类型

**实际问题**：传感器编号、采样次数和温度看起来都是“数据”，但它们允许的值和操作不同。如果只说“定义一个变量存数字”，后续就很难准确解释指针指向什么、引用绑定什么、对象何时结束生命。

先看一行代码，不急着拆语法：

```cpp
int sample_count{0};
```

直观上，可以问四个不同问题：运行时存在的实体是什么？代码用哪个名字访问它？它当前表达什么信息？哪套规则约束它？

**概念落点**：

- [对象（object）](../docs/glossary.md#对象object)是程序执行期间占据一段存储、具有类型，并可表示值的实体。上例运行时建立了一个 `int` 对象。
- [变量（variable）](../docs/glossary.md#变量variable)是由声明引入的具名对象或具名引用。上例的变量名是 `sample_count`；引用到第 6 天再展开。
- [值（value）](../docs/glossary.md#值value)是对象能够表示或表达式求值能够产生的抽象信息。该对象当前表示整数值 `0`。
- [类型（type）](../docs/glossary.md#类型type)是 C++ 对对象、引用、函数和表达式进行分类的规则系统，它规定可表示的值、允许的操作及相关语义约束。这里的类型是 `int`。

把这四层对应回代码：

| 观察角度 | `int sample_count{0};` 中的答案 | 它不等于什么 |
|---|---|---|
| 对象 | 执行期间建立的那个 `int` 实体 | 不等于对象当前的值 |
| 变量 | 名称 `sample_count` 引入的具名对象 | 不要求“变量”一定可修改，`const` 变量仍是变量 |
| 值 | 当前的抽象信息 `0` | 不等于名称，也不等于固定字节图案 |
| 类型 | `int` 及其规则 | 不只是“占多少字节” |

**代码与机制**：对象需要存储，但 C++ 标准不保证每个变量都对应一个始终可见的栈地址。编译器可以在不改变标准所要求程序表现的前提下使用寄存器、消除不必要存储或改写指令。今天建立的是语言模型，不把某一种机器布局误写成定义。

下面三行使用三种基本类型表达不同业务含义：

```cpp
const int sensor_id{12};
int sample_count{0};
double temperature_celsius{21.75};
```

| 类型 | 这里适合表达 | 必须守住的边界 |
|---|---|---|
| `int` | 有正负的整数计数或编号 | 标准不保证所有实现中都恰好为 4 字节 |
| `double` | 含小数的近似数值 | 许多十进制小数不能被二进制浮点精确表示 |
| `bool` | `true` / `false` 两种逻辑状态 | 不适合偷偷承载三种以上业务状态 |

**错误做法与修复**：把需要保留小数的温度设计成 `int`，再写 `int temperature = 21.75;`。对这个具体值，转换会舍去小数部分，程序得到 `21`；这是**有明确定义但结果可能不符合需求**，不是“必然编译错误”。修复应从业务含义出发选择 `double`，并让编译器帮助拒绝意外窄化，见机制三。

**小检查**：在 `double temperature{21.75};` 中，名称、对象、类型和值分别是什么？删除名称是否意味着 C++ 中就不可能存在对象？

### 机制二：初始化建立初始状态，赋值修改既有状态

**实际问题**：采样次数应该从一个可解释的状态开始。如果把“对象刚建立”和“对象已经存在后再次改变”混为一谈，就会误判未初始化读取，也会看不懂类的构造与赋值差异。

**概念落点**：

- [初始化（initialization）](../docs/glossary.md#初始化initialization)是在对象被创建时确定其初始状态的过程。
- [赋值（assignment）](../docs/glossary.md#赋值assignment)是在对象已经完成初始化之后，用赋值运算修改其当前值或状态的操作。

判断方法不是“代码里有没有 `=`”，而是先问：**此刻是否正在创建对象？**

```cpp
int first_count{0};    // 创建对象：初始化
int second_count = 0;  // 创建对象：仍是初始化
int third_count(0);    // 创建对象：仍是初始化

first_count = 1;       // 对象已经存在：赋值
```

| 代码 | 对象此前是否已存在 | 分类 |
|---|---:|---|
| `int count{0};` | 否 | 初始化 |
| `int count = 0;` | 否 | 初始化；这里的 `=` 不把整条声明变成赋值 |
| `count = 1;` | 是 | 赋值 |

**代码与机制**：对于今天的 `int` 和 `double`，初始化与赋值最后都可能表现为对象保存了某个值，所以初学者容易觉得它们“没有区别”。但语言规则选择发生在不同时间：初始化参与建立对象，赋值操作一个已建立对象。到第 9—10 天，类对象可能调用构造函数或赋值运算符，差异会直接影响资源管理。

函数体内写下：

```cpp
int sample_count;
std::cout << sample_count << '\n';  // 故意错误
```

对这个 C++17 局部 `int` 对象，声明没有给它确定的初始值；随后读取不确定值会触发**未定义行为**。标准不保证输出 `0`、某个“随机数”或发生崩溃。正确做法是在首次需要的地方直接给出有意义初值：`int sample_count{0};`。

**错误做法与修复**：先写 `int count;`，经过多条分支后才尝试赋值，并假设每条路径都覆盖。这样增加了“使用前未赋值”的风险。修复优先是把声明移动到初值已经可用的位置并直接初始化，而不是用一个没有业务意义的值掩盖流程问题。

**小检查**：为什么 `int count = 0;` 属于初始化，而下一行 `count = 1;` 才属于赋值？

### 机制三：花括号初始化让意外窄化尽早变成编译错误

**实际问题**：温度 `21.75` 被悄悄放进整数后变为 `21`，程序可能成功构建，却把精度问题带到运行结果中。我们希望在明显的类型选择冲突处尽早得到诊断。

**概念落点**：花括号形式 `{...}` 在这里执行列表初始化。它仍属于初始化，不是一个新的对象阶段。C++11 引入的列表初始化会拒绝语言规定的窄化转换；例如从 `double` 的 `21.75` 初始化 `int`。

```cpp
int temperature{21.75};  // 故意错误：列表初始化发生窄化，程序非良构
```

这不是“可能给警告”，而是程序必须被诊断。根据需求有两种诚实的修复方向：

```cpp
double temperature{21.75};  // 需求需要小数
int temperature{21};        // 需求明确只使用整数
```

**代码与机制**：列表初始化在选择和转换初始值时应用窄化检查。它能阻止不少明显的信息丢失，但不是“任何精度问题检测器”：`double temperature{0.1};` 本身合法，却仍受浮点近似表示约束。对类类型，花括号还可能影响构造函数选择；那是第 9、14 天的内容，不能把今天针对基本类型的建议扩大成无条件规则。

对本阶段的基本数值类型，可以把“声明处给出有意义初值，优先使用花括号观察窄化诊断”作为安全默认习惯。

**错误做法与修复**：看到窄化诊断后用强制转换压掉错误，却没有先回答“业务是否允许丢失小数”。这可能把编译器发现的设计问题变成**有明确定义但结果不符合预期**。修复顺序应是先确认业务，再选类型；确需转换时才显式表达转换意图并检查范围。

**小检查**：`int value = 21.75;` 与 `int value{21.75};` 的构建结果为何不同？花括号又为什么不能保证所有浮点数都精确？

### 机制四：`const` 把“不应再改”交给类型系统检查

**实际问题**：传感器编号在一次运行中应保持不变。如果只写注释“不要修改”，后续代码仍可意外赋值；我们希望让错误在构建阶段暴露。

**概念落点**：[const 限定（const qualification）](../docs/glossary.md#const-限定const-qualification)表示程序不得通过相应对象的普通访问方式修改其值或状态。它决定哪些修改表达式会被拒绝；它不等于“值必定在编译期已知”，也不规定对象必须位于硬件只读内存。

```cpp
const int sensor_id{12};
int sample_count{0};

sample_count = 1;  // 合法：这个状态本来就需要变化
sensor_id = 13;    // 故意错误：不能给 const int 对象赋值
```

**代码与机制**：`const` 是类型系统中的约束。对于今天的 `const int`，创建时必须得到初值，因为之后不能再用普通赋值补上。编译器可以利用该约束检查代码或进行优化，但“可以优化”不等于标准规定某个物理存储区。

初值也可以在运行时取得：

```cpp
int read_sensor_id() {
    return 12;
}

const int sensor_id{read_sensor_id()};
```

这里的函数可以在运行时执行，`sensor_id` 仍是 `const`：它表达的是初始化之后不能通过该对象普通修改，而不是承诺初始化表达式必定在编译期求值。

**错误做法与修复**：为了消除 `sensor_id = 13;` 的编译错误，机械地删除所有 `const`。这会同时删除有价值的设计约束。正确修复要回到需求：编号确实固定，就删除错误赋值；编号本来会变化，才把相应状态设计为非 `const`。

**小检查**：为什么“运行时读取到的值”仍然可以初始化 `const` 对象？`const` 到底约束的是哪个时间段的操作？

## 💻 最小可运行示例

完整代码位于 [`examples/day02/main.cpp`](../examples/day02/main.cpp)。

```cpp
#include <iostream>

int main() {
    const int sensor_id{3};
    int sample_count{0};
    double temperature_celsius{21.75};

    std::cout << "sensor: " << sensor_id << '\n';
    std::cout << "sample " << sample_count << ": "
              << temperature_celsius << " C\n";

    sample_count = 1;
    temperature_celsius = 22.125;

    std::cout << "sample " << sample_count << ": "
              << temperature_celsius << " C\n";
    return 0;
}
```

预期输出：

```text
sensor: 3
sample 0: 21.75 C
sample 1: 22.125 C
```

观察重点：三个对象都在声明时初始化；之后只给两个非 `const` 对象赋值；`sensor_id` 保持不变。

## 🎤 高频面试实战

### 题 1：初始化和赋值有什么区别？为什么推荐列表初始化？

**30 秒口头回答**：初始化在对象创建时建立初始状态，赋值是在对象已经初始化之后修改当前状态。`int count = 0;` 虽然有等号，仍然是初始化。花括号初始化表达清晰，并会拒绝很多窄化转换，例如 `int value{3.5}` 是编译错误；但它不是所有类型问题的万能检查器。

**完整答题逻辑**：先按发生时机区分，再比较最小代码，最后说明列表初始化的价值和边界。对于基本类型，二者表面都像写入值；对于类类型，它们可能分别选择构造和赋值操作，后续课程展开。

**可能连续追问**：

- `int x = 1;` 中的 `=` 为什么不是赋值？
- `int x;` 是否一定初始化为 0？
- 花括号为什么会拒绝 `int x{3.5};`？
- 初始化与赋值对类对象可能有什么不同？

**容易失分的说法**：根据是否出现 `=` 判断赋值；断言所有未显式初始化的整数都是 0；声称花括号能够阻止一切精度问题。

### 题 2：`const` 对象一定是编译期常量吗？

**30 秒口头回答**：不一定。`const` 的核心含义是不能通过相应对象的普通访问方式修改它；初始化值可以在运行时得到。因此“初始化后不可普通修改”和“编译期可求值”是两个不同问题。具体编译期常量规则需要结合表达式和语言版本判断。

**完整答题逻辑**：先给出 `const` 的修改约束，再举 `const int id{runtime_sensor_id()};`，说明函数结果可在运行时产生；最后强调 `const` 也不保证某种物理存储位置。

**可能连续追问**：

- `const` 对象为什么通常必须初始化？
- `const` 是否意味着一定放在只读段？
- `const` 与编译期求值概念有什么区别？
- 指针上的 `const` 有哪些位置差异？

最后一个追问会在第 6 天结合指针正式回答。

**容易失分的说法**：把 `const` 等同于宏；声称所有 `const` 值都在编译期确定；声称它们一定存放在只读内存。
