## 📖 核心知识重构

这一部分不先背一组孤立名词。我们从一个真实任务开始：`main.cpp` 要输出传感器状态，而状态计算放在另一个文件中。每遇到一个新问题，再在代码所在的语境中建立术语。

### 机制一：函数把一段行为变成可检查的调用

**实际问题**：如果“计算状态码”的代码散落在多个位置，修改规则时容易漏改。我们希望给这段行为一个稳定入口。

**概念落点**：先把函数直观地看成“有调用入口的一段行为”。准确地说，[函数（function）](../docs/glossary/day01.md#函数function)是可被调用以执行一组语句的程序实体，并具有确定的名称或调用方式、输入形式和返回类型。这个定义决定调用形式和返回类型，却不保证函数逻辑正确，也不保证调用所需的其他定义已经进入最终程序。

```cpp
int status_code() {
    return 7;
}
```

逐行看这段代码：

- `int` 表示调用结果的类型；类型会在第 2 天系统学习。
- `status_code` 是函数名称。
- `()` 表示今天这个函数不接收参数；参数在第 4 天展开。
- `{ return 7; }` 是函数体，描述调用后执行什么以及返回什么。

**代码与机制**：调用表达式 `status_code()` 不是把函数体复制到当前位置，而是表达“调用这个函数并取得结果”。编译器可以决定是否内联等实现细节；C++ 的语义要求不等于“运行时一定发生某种固定的跳转指令”。

**错误做法与修复**：把 `int status_code();` 当成“函数已经实现”，之后直接交付。它只告诉调用方调用形式，没有函数体；若程序需要该定义却找不到，通常出现**链接错误**。修复是在参与构建的源文件中提供相符函数体。

**小检查**：在 `int status_code() { return 7; }` 中，哪一部分让它不仅是一个名字说明，而且拥有可执行内容？
	函数体。
### 机制二：声明先建立可见接口，定义再提供完整内容

**实际问题**：`main.cpp` 调用另一个文件中的 `status_code` 时，编译器需要先检查名称、参数和返回类型，但不必在同一位置看到函数体。大型工程也不能要求每个调用方都复制实现。

**概念落点**：

- [声明（declaration）](../docs/glossary/day01.md#声明declaration)把一个名称引入或重新引入程序，并说明该名称所指实体的必要属性。
- [定义（definition）](../docs/glossary/day01.md#定义definition)是一种声明，它为被定义的实体提供程序所要求的完整定义；例如函数定义提供函数体。

因此二者不是互斥关系，而是包含关系：**定义也是声明，但声明不一定是定义**。

```cpp
int status_code();              // 声明，不含函数体

int status_code() {             // 定义，同时也是声明
    return 7;
}
```

**代码与机制**：本课程把共享声明放入 `status.hpp`，把函数定义放入 `status.cpp`。`main.cpp` 包含头文件后，可以依据声明检查 `status_code()` 的调用；最终构建仍要找到相符定义。头文件如何被纳入编译输入会在第 22 天讲预处理时展开，今天只需把“调用处需要接口信息”和“完整程序需要实现”分开。

声明与定义必须相符。例如，声明是 `int status_code();`，定义却写成 `double status_code()`，不是“差不多同一个函数”。编译器或链接器会依据可见代码和构建方式给出诊断，不能依赖某一种固定报错文本。

**错误做法与修复**：

- 只有声明、没有所需定义：源码可能分别通过检查，最终通常是**链接错误**。
- 调用前连声明也不可见：编译器无法判断名称和调用形式，属于**编译错误**。
- 在多个普通源文件中提供不允许重复的定义：违反定义规则，常见结果是链接诊断；更完整的一处定义规则在第 22 天串联。

**小检查**：为什么在 `main.cpp` 中再写一遍 `int status_code();` 不能修复“缺少实现”？
	只有函数的声明，没有函数的定义，即代码的具体实现内容。
### 机制三：编译与链接把不同问题分成不同阶段

**实际问题**：一个多文件程序失败时，只说“编译不过”会把搜索范围混在一起。我们需要知道失败发生在单个编译输入的检查阶段，还是多个结果的组合阶段。

**概念落点**：

- 在本课程的构建语境中，[编译（compilation）](../docs/glossary/day01.md#编译compilation)是把每个源文件及其包含内容分别翻译并进行语法、类型等检查，生成可供后续组合使用结果的过程。
- 在常见 C++ 构建模型中，[链接（linking）](../docs/glossary/day01.md#链接linking)是组合分别翻译得到的结果和所需库，并解析跨文件实体引用以形成可执行程序或库的过程。

把三个文件放到构建流程中看：

| 输入或阶段 | 此时已知什么 | 此时还不能证明什么 |
|---|---|---|
| 编译 `main.cpp` | `status.hpp` 提供了可检查的函数声明 | `status_code` 的定义一定存在 |
| 编译 `status.cpp` | 函数体符合当前可见声明 | 其他所有源文件都已加入目标 |
| 链接两份结果 | 跨文件调用能否找到相符定义 | 业务结果一定正确、运行一定安全 |

**代码与机制**：主流 GCC/Clang 工具链可以显式分成下面几步：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -c main.cpp
c++ -std=c++17 -Wall -Wextra -Wpedantic -c status.cpp
c++ main.o status.o -o day01_example
```

也可以用一条命令驱动这些步骤：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic main.cpp status.cpp -o day01_example
```

这里要守住标准边界：`.o` 文件、独立链接器进程和命令名称属于常见实现模型。C++ 标准规定翻译与程序语义要求，但不强制工具链必须长成这一种样子。

**错误做法与修复**：只把 `main.cpp` 加入最终构建，漏掉 `status.cpp`。调用处能依据声明通过编译，但组合时找不到所需定义，属于**链接错误**。应检查构建目标包含的源文件和库，而不是盲目修改函数内部逻辑。

**小检查**：如果缺少分号，为什么通常还没机会进入链接阶段？

### 机制四：按最早失败阶段分类，才能选择正确证据

**实际问题**：“程序不工作”可能表示构建失败、启动后终止、结果算错，也可能表示代码已经越出标准允许推理的范围。这几类问题需要不同证据。

**概念落点**：[未定义行为（undefined behavior, UB）](../docs/glossary/day01.md#未定义行为undefined-behavior-ub)是 C++ 标准对其结果不作任何要求的行为。它与普通逻辑错误不同：逻辑错误仍在语言规则内运行，只是结果不符合需求；UB 则不能用标准保证某个固定结果。

| 类别 | 最早暴露位置 | 最小例子 | 优先收集的证据 |
|---|---|---|---|
| 编译错误 | 单个编译输入的翻译与检查 | 缺少分号、名称不可见、类型不匹配 | 首条编译诊断及对应源码 |
| 链接错误 | 分别翻译结果的组合 | 有函数声明和调用，但定义未参与链接 | 构建目标、函数签名、链接库 |
| 运行时失败 | 程序已经开始执行 | 未捕获异常导致程序终止 | 错误信息、输入、调用栈 |
| 逻辑错误 | 程序完成执行但结果违背需求 | 温度换算公式写错 | 需求、测试、关键中间值 |
| 未定义行为 | 执行了标准不约束的操作 | 解引用空指针 | 语言规则、警告、Sanitizer；不能猜固定现象 |

**代码与机制**：分类依据是“最早在哪个阶段已经足以判定失败”，而不是终端里有没有出现红字。编译、链接成功只排除了相应阶段已检测到的问题；它们不证明所有执行路径都正确。Sanitizer 能帮助发现一部分运行期问题，但也不是“没有报告就证明不存在 UB”。

**错误做法与修复**：把 UB 说成“必然段错误”。这是不准确的面试表达，因为崩溃、看似正常或其他现象都可能出现。修复说法应为：**结果不可由 C++ 标准预测；需要移除触发 UB 的操作，而不是依赖某次运行现象。**

**小检查**：程序输出了一个稳定但错误的温度，且使用的所有操作都有定义。它首先应归为哪一类？为什么不是 UB？

## 💻 最小可运行示例

```cpp
#ifndef CPP_LEARNING_DAY01_STATUS_HPP

#endif
```

```cpp
#include "status.hpp"

int status_code() {
    return 7;

```

```cpp
#include "status.hpp"

#include <iostream>

int main() {
    std::cout << "sensor status: " << status_code() << '\n';
    return 0;
}
```

预期输出：

```text
sensor status: 7
```

## 🎤 高频面试实战

### 题 1：编译错误和链接错误有什么区别？

**30 秒口头回答**：编译错误发生在某个源文件被翻译和检查时，例如语法错误、名称不可见或类型不匹配。链接错误发生在分别翻译的结果被组合时，例如调用已有声明，但对应定义未参与链接。主流工具链通常分别报告两类错误，但标准不强制具体文件格式或独立链接器进程。

**完整答题逻辑**：先说发生阶段，再给最小例子，最后说明排查入口。编译错误优先看首条诊断和当前文件；链接错误优先核对函数签名、实现文件是否加入目标、库是否正确链接。

**可能连续追问**：

- 为什么只有声明时调用仍可能通过编译？
- “undefined reference”一定是没有写实现吗？也可能是签名不一致或库顺序/配置问题吗？
- C++ 标准是否规定必须生成目标文件？

**容易失分的说法**：把所有构建失败统称为编译错误；声称链接错误只可能由“忘记写函数体”造成；把 `.o` 和独立链接器说成标准强制。

### 题 2：声明和定义是什么关系？

**30 秒口头回答**：声明引入名称并给出引用它所需的信息；定义是一种声明，还提供实体所需的完整定义，例如函数体。不是每个声明都是定义，但定义也是声明。调用函数时编译阶段可以只看到声明，程序最终仍需要满足定义规则。

**完整答题逻辑**：先给包含关系，再用 `int f();` 与 `int f() { return 1; }` 对比，最后说明头文件通常放声明、源文件放定义以及二者必须一致。

**可能连续追问**：

- 变量声明和函数声明是否完全相同？
- 为什么头文件中可以定义某些 `inline` 函数？
- 重复定义为什么有时链接失败、有时涉及更复杂的规则？

这些追问涉及第 5、14、22 天内容；今天只需明确条件，不提前背细节。

**容易失分的说法**：说“声明永远不分配空间，定义永远分配空间”；说声明和定义互斥；忽略函数签名必须相符。
