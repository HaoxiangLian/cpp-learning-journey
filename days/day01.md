## 📚 今日术语卡

### 函数（function）

直观模型：给一段可重复执行的代码起名字，需要时调用它。

正式定义、边界、示例与误解见[术语表：函数](../docs/glossary.md#函数function)。今天只要求认出函数声明、函数定义和调用；参数设计在第 4 天展开。

### 声明（declaration）与定义（definition）

直观模型：声明告诉当前文件“有这样一个名称及其形式”；定义进一步提供程序需要的完整内容。

唯一正式定义见[术语表：声明](../docs/glossary.md#声明declaration)和[术语表：定义](../docs/glossary.md#定义definition)。声明不一定是定义，但定义也是声明。

### 编译（compilation）与链接（linking）

直观模型：先分别检查并翻译每个源文件，再把它们和库组合起来。

唯一正式定义见[术语表：编译](../docs/glossary.md#编译compilation)和[术语表：链接](../docs/glossary.md#链接linking)。目标文件与独立链接器属于主流实现模型，不是标准强制的文件或进程形态。

### 未定义行为（undefined behavior, UB）

直观模型：代码越出了 C++ 标准允许你推理的范围。

唯一正式定义见[术语表：未定义行为](../docs/glossary.md#未定义行为undefined-behavior-ub)。它不等于“必然段错误”。今天只建立边界，具体诱因会在后续对象、指针和并发课程中学习。

## 📖 核心知识重构

### 机制一：从源文件到程序

1. **实际问题**：工程会把入口、传感器读取和任务逻辑拆到不同文件。我们需要分别修改和检查它们，最后得到一个程序。
2. **定义与设计取舍**：编译让源文件可以分别翻译，链接再解析跨文件引用。代价是错误被分成不同阶段，必须依据阶段定位。
3. **底层机制**：常见工具链把每个源文件翻译为包含机器代码与元数据的目标文件，再由链接器组合。C++ 标准只规定程序的翻译和语义要求，不强制 `.o` 文件、命令名或具体链接器。
4. **错误做法与后果**：只把 `main.cpp` 交给最终构建，却漏掉包含实现的 `status.cpp`。`main.cpp` 可以通过编译，但跨文件引用找不到定义，属于**链接错误**。修复是把实现文件加入同一构建目标。

常见命令分解：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -c main.cpp
c++ -std=c++17 -Wall -Wextra -Wpedantic -c status.cpp
c++ main.o status.o -o day01_example
```

也可以一步完成：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic main.cpp status.cpp -o day01_example
```

### 机制二：声明让调用可检查，定义让调用可实现

1. **实际问题**：`main.cpp` 调用另一个文件的 `status_code` 时，编译器需要先知道这个名称怎样调用，但不必同时看到函数体。
2. **定义与设计取舍**：头文件放声明，实现文件放定义，可以让多个调用方共享同一份接口信息。代价是声明与定义必须保持一致。
3. **底层机制**：编译 `main.cpp` 时，声明足以检查调用形式；链接时，构建结果仍必须找到所需定义。头文件由预处理包含进源文件，这一机制在第 22 天正式展开。
4. **错误做法与后果**：只写 `int status_code();` 而从未提供函数体。调用处语法合法，但最终缺少定义，通常是**链接错误**。修复是在一个参与构建的 `.cpp` 中提供相符定义。

### 机制三：按失败阶段定位，而不是只说“代码报错”

1. **实际问题**：同一句“程序不工作”可能需要完全不同的排查手段。
2. **定义与设计取舍**：先按失败发生阶段分类，再分析具体原因，可以缩小搜索范围。
3. **底层机制**：语法或类型检查通常在编译阶段；跨文件引用解析通常在链接阶段；进程启动后的异常终止属于运行时失败；输出合法但需求不符属于逻辑错误。UB 则表示标准不约束结果，它可能在任何表象下出现。
4. **错误做法与后果**：把 UB 说成“必然崩溃”属于**有明确定义但结论不符合标准边界的错误说法**。正确表达是：结果不可由 C++ 标准预测，崩溃只是可能现象之一。

| 类别 | 发生位置 | 示例 | 先检查什么 |
|---|---|---|---|
| 编译错误 | 单个编译输入的翻译/检查 | 缺少分号、名称未声明、类型不匹配 | 诊断位置与首条错误 |
| 链接错误 | 跨文件或库的组合 | 声明后调用，但实现未参与链接 | 构建目标、签名、库 |
| 运行时失败 | 程序开始运行后 | 未捕获异常导致终止 | 输入、调用栈、错误信息 |
| 逻辑错误 | 程序正常运行但结果违背需求 | 把摄氏温度公式写错 | 需求、测试与中间值 |
| 未定义行为 | 代码执行了标准不约束的操作 | 解引用空指针 | 语言规则、Sanitizer；不要猜固定结果 |

## 💻 最小可运行示例

完整文件位于 [`examples/day01/`](../examples/day01/)。

`status.hpp` 只放声明：

```cpp
#ifndef CPP_LEARNING_DAY01_STATUS_HPP
#define CPP_LEARNING_DAY01_STATUS_HPP

int status_code();

#endif
```

`status.cpp` 提供定义：

```cpp
#include "status.hpp"

int status_code() {
    return 7;
}
```

`main.cpp` 调用函数：

```cpp
#include "status.hpp"

#include <iostream>

int main() {
    std::cout << "sensor status: " << status_code() << '\n';
    return 0;
}
```

预期输出：

```text
sensor status: 7
```

## 🐛 错误代码诊断

下面代码被显著标注为故意错误，文件位于 [`exercises/day01/broken/missing_definition_main.cpp`](../exercises/day01/broken/missing_definition_main.cpp)，不进入正常构建目标。

```cpp
// INTENTIONALLY INVALID: link-error exercise.
#include <iostream>

int status_code();

int main() {
    std::cout << status_code() << '\n';
}
```

判断：这段源码本身通常可以编译，但若没有任何参与链接的文件定义 `status_code`，最终构建出现**链接错误**。它不是 UB，也不能靠在调用处再写一次相同声明修复。修复是在参与构建的源文件中提供相符定义。

另一个故意错误见 [`syntax_error.cpp`](../exercises/day01/broken/syntax_error.cpp)：缺少分号属于**编译错误**，链接阶段尚未开始。

## 🎤 高频面试实战

### 题 1：编译错误和链接错误有什么区别？

**30 秒口头回答**：编译错误发生在某个源文件被翻译和检查时，例如语法错误、名称不可见或类型不匹配。链接错误发生在分别翻译的结果被组合时，例如调用已有声明，但对应定义未参与链接。主流工具链通常分别报告两类错误，但标准不强制具体文件格式或独立链接器进程。

**完整答题逻辑**：先说发生阶段，再给最小例子，最后说明排查入口。编译错误优先看首条诊断和当前文件；链接错误优先核对函数签名、实现文件是否加入目标、库是否正确链接。

**可能连续追问**：

- 为什么只有声明时调用仍可能通过编译？
- “undefined reference”一定是没有写实现吗？也可能是签名不一致或库顺序/配置问题吗？
- C++ 标准是否规定必须生成目标文件？

**容易失分的说法**：把所有构建失败统称为编译错误；声称链接错误只可能由“忘记写函数体”造成；把 `.o` 和独立链接器说成标准强制。

### 题 2：声明和定义是什么关系？

**30 秒口头回答**：声明引入名称并给出引用它所需的信息；定义是一种声明，还提供实体所需的完整定义，例如函数体。不是每个声明都是定义，但定义也是声明。调用函数时编译阶段可以只看到声明，程序最终仍需要满足定义规则。

**完整答题逻辑**：先给包含关系，再用 `int f();` 与 `int f() { return 1; }` 对比，最后说明头文件通常放声明、源文件放定义以及二者必须一致。

**可能连续追问**：

- 变量声明和函数声明是否完全相同？
- 为什么头文件中可以定义某些 `inline` 函数？
- 重复定义为什么有时链接失败、有时涉及更复杂的规则？

这些追问涉及第 5、14、22 天内容；今天只需明确条件，不提前背细节。

**容易失分的说法**：说“声明永远不分配空间，定义永远分配空间”；说声明和定义互斥；忽略函数签名必须相符。
