## 📖 核心知识重构

今天研究的不是“怎样把错误藏起来”，而是：**失败发生时，已经建立的对象和资源怎样有序结束，原对象还保留哪些可依赖状态。** “语言规则/标准语义”是所有符合 C++17 的实现都要保持的代码含义；“实现方式/实现模型”是编译器和运行环境实现这些规则的具体做法，不能把调用帧布局或寄存器选择写成标准保证。

### 机制一：RAII 让普通返回和异常共用清理路径

**实际问题**：函数打开设备后有三处可能提前返回，还可能抛异常。若每个出口都手写 `close()`，漏掉一处就会占住设备。先看 9 行代码：

```cpp
class Session {
public:
    Session() { std::cout << "open\n"; }
    ~Session() { std::cout << "close\n"; }
};

void run() {
    Session session;
    throw std::runtime_error{"lost"};
}
```

这里只有一个 `Session` 对象，它代表一段需要结束的使用关系。进入 `run` 时对象建立；执行 `throw` 后，后续普通语句不再执行，但离开 `run` 前 `session` 仍会销毁并输出 `close`。离开后不能再使用 `session`。

| 时刻 | `session` | 资源状态 |
|---|---|---|
| 进入 `run` 前 | 尚未创建 | 尚未取得 |
| 构造完成 | 可用 | 已由 `session` 管理 |
| 执行 `throw` | 即将离开作用域 | 仍由 `session` 管理 |
| 离开 `run` | 已销毁，不能再用 | 析构过程已清理 |

**概念落点**：这就是 [RAII（resource acquisition is initialization）](../docs/glossary/day19.md#raiiresource-acquisition-is-initialization)：RAII 是把资源的有效使用期绑定到对象生命周期的 C++ 设计方法：对象初始化时建立资源管理责任，对象销毁时由析构过程自动结束该资源。

**代码与机制**：构造完成后，`session` 才承担管理责任；无论 `run` 从右花括号返回、提前 `return`，还是因异常离开，语言都沿对象销毁规则调用析构过程。RAII 不只管理内存，文件、互斥量、设备会话都可封装；`vector`、`string` 和智能指针也是现成管理类型。标准保证对象生命周期和析构语义，不规定资源对象必须放在所谓“栈区”的固定物理位置。

**错误做法与修复**：

- **资源泄漏**：先调用 `open()`，在多个失败出口分别手写 `close()`。修复为创建专门管理对象，让一个析构路径覆盖所有出口。
- **重复清理/未定义行为风险**：两个对象都认为自己独占同一原始句柄。修复为让所有权唯一，或使用明确的共享管理协议。
- **设计错误**：析构函数直接抛出清理异常。异常传播期间再次抛出可能终止程序；析构应处理内部失败，需向调用者报告时另设显式 `close()`。

**小检查**：`throw` 执行后，为什么函数体后面的语句没运行，`Session` 的析构过程却仍运行？

### 机制二：异常传播先结束沿途对象，再进入匹配处理器

**实际问题**：底层读取失败，究竟由哪一层处理？失败从 `read()` 经过 `process()` 到 `main()`：

```cpp
void read() {
    throw std::runtime_error{"offline"};
}

void process() {
    Session session;
    read();
}

try { process(); }
catch (const std::exception& error) { /* 处理 */ }
```

有一个异常对象和一个 `session` 局部对象。`read` 抛出后，控制流不再回到 `process` 的下一条普通语句；离开 `process` 时 `session` 被销毁，然后外层匹配的 `catch` 开始处理。`catch` 结束后，异常对象也不再供该处理器使用。

| 执行阶段 | 发生什么 |
|---|---|
| 调用 `process` | 创建 `session` |
| 进入 `read` | 准备读取 |
| `throw` | 建立异常并寻找处理器 |
| 离开 `process` | 销毁 `session` |
| 进入 `catch` | 通过 `error` 读取失败信息 |

**概念落点**：这就是 [异常传播与栈展开（exception propagation and stack unwinding）](../docs/glossary/day19.md#异常传播与栈展开exception-propagation-and-stack-unwinding)：异常传播是 `throw` 产生的异常沿调用关系寻找匹配处理器的过程；栈展开是在这段离开路径上按规则销毁已经成功构造的自动对象的过程。

**代码与机制**：`throw` 之后寻找类型匹配的 `catch`；这里用 `const std::exception&` 避免复制切片，并能处理常见标准异常派生类。找到处理器前，每个已离开的作用域都销毁其中已成功构造的自动对象。如果构造函数只完成了部分成员就抛出，完整外层对象没有构造成功，因此不调用它自己的析构函数，但已成功构造的成员会逆序销毁。调用帧怎样组织只是实现模型；初学者只需按“抛出→沿途对象结束→进入匹配 `catch`”预测。

**错误做法与修复**：

- **错误处理缺失**：异常一路找不到处理器，最终调用 `std::terminate`；这不是“异常一定能自动恢复”。修复为在真正能决定恢复策略的边界处理。
- **信息丢失**：写 `catch (std::exception error)` 按值捕获派生异常，可能切片。修复为 `catch (const std::exception& error)`。
- **状态误判**：以为异常会从失败行后继续执行。修复为沿调用关系画出实际跳转和对象结束顺序。

**小检查**：`process()` 中 `read()` 后面若有一行输出，异常发生时它会执行吗？`session` 又在什么时候销毁？

### 机制三：异常安全等级回答“失败后还能依赖什么”

**实际问题**：配置原值为 20，调用 `set_level(config, -5)` 失败后，值应该是 20、-5，还是半更新状态？先看最小顺序：

```cpp
void set_level(int& level, int candidate) {
    if (candidate < 0 || candidate > 100) {
        throw std::invalid_argument{"bad level"};
    }
    level = candidate;
}
```

这里只有已有的 `level` 对象和形参 `candidate` 对象。检查阶段没有改 `level`；不合法就抛出，因此返回调用方后 `level` 仍是 20。合法时最后一行才提交新值。异常后 `candidate` 已结束，调用方的 `level` 仍可使用。

**概念落点**：这就是 [异常安全保证（exception safety guarantee）](../docs/glossary/day19.md#异常安全保证exception-safety-guarantee)：异常安全保证是操作发生异常时对程序状态和资源作出的承诺：基本保证要求状态仍有效且无资源泄漏，强保证进一步要求对外状态保持调用前的样子，不抛保证则承诺异常不会离开该操作。

**代码与机制**：基本保证允许值改变，但对象必须仍满足可用约束且资源不泄漏；强保证让失败对外像没有发生；不抛保证承诺操作一定不会让异常离开。示例采用“先准备、后提交”：所有可能失败的检查先完成，最后用不会失败的简单赋值提交。复杂对象常先在临时对象中完成工作，再通过合适的交换或移动提交；但整个函数的等级不会凭口号自动成立，必须检查每一步的保证。

**错误做法与修复**：

- **强保证破坏**：先写 `level = candidate`，再检查并抛异常，失败后旧值已经丢失。修复为先验证后提交。
- **概念错误**：声称“基本保证就是值不变”。基本保证只承诺有效和无泄漏；若业务要求值不变，应明确实现强保证。
- **过度捕获**：每层都 `catch (...)` 后忽略错误，只让状态更难判断。修复为只在能恢复、补充上下文或转换错误协议的边界捕获。

**小检查**：一个函数失败后对象仍合法但部分字段已改变，它满足哪一级保证？为什么不一定满足强保证？

### 机制四：`noexcept` 是边界承诺，不是自动防护罩

**实际问题**：容器移动元素时，希望知道移动操作是否会失败；析构清理也不应让异常逃出。先看声明和检查：

```cpp
void close_device() noexcept {
    // 内部处理清理失败，不让异常越过边界
}

static_assert(noexcept(close_device()));
```

调用中没有新建业务对象；变化的是接口契约：调用者可以依赖异常不会从 `close_device` 离开。函数内部仍能调用可能失败的代码，但必须在边界内处理；若异常真的逃出，程序不能再按普通 `catch` 路径继续，而会调用 `std::terminate`。

**概念落点**：这就是 [`noexcept` 说明（noexcept specification）](../docs/glossary/day19.md#noexcept-说明noexcept-specification)：`noexcept` 说明是函数类型的一部分，用来承诺异常不会越过该函数调用边界；若异常仍从不抛函数逃出，运行时调用 `std::terminate`。

**代码与机制**：`noexcept(close_device())` 是编译期查询表达式，得到 `true`。标准库可根据移动构造是否 `noexcept` 决定扩容时是否优先移动，以便维持自己的异常安全保证。析构函数通常具有不抛语义，清理代码应避免异常外逃。`noexcept` 影响可观察契约与泛型选择，不只是性能提示；它也不负责自动捕获或记录错误。

**错误做法与修复**：

- **终止风险**：把可能抛出的函数随手标成 `noexcept`，异常逃出后调用 `std::terminate`。修复为先保证内部处理完整，或不要作虚假承诺。
- **接口错误**：可合理向调用者报告失败的主要业务操作一律标 `noexcept`。修复为按真实失败协议设计。
- **清理错误**：析构中直接抛异常。修复为内部吞并并记录不可传播错误，或提供显式、可检查的关闭函数。

**小检查**：`noexcept` 函数体内出现 `throw` 是否必然编译失败？异常越过函数边界时会发生什么？

## 🐛 错误代码诊断

| 现象 | 分类 | 后果边界 | 修复方向 |
|---|---|---|---|
| 多个返回点手写同一资源清理 | 资源管理错误 | 某条失败路径可能泄漏，但不保证立刻崩溃 | 用 RAII 管理对象统一析构路径 |
| 按值捕获 `std::exception` | 类型/信息错误 | 派生部分可能切片 | 按 `const std::exception&` 捕获 |
| 先修改状态再做会抛的检查 | 异常安全错误 | 失败后留下部分新状态 | 先准备与验证，最后提交 |
| 异常逃出 `noexcept` 函数 | 契约违约 | 调用 `std::terminate` | 修正声明或在边界内处理 |
| 异常传播期间析构再抛 | 终止风险 | 可能因第二个活动异常调用 `std::terminate` | 析构保持不抛，另设显式报告接口 |

### 题 1：什么是 RAII？异常发生时为什么仍能避免资源泄漏？

**30 秒回答**：RAII 把资源管理责任绑定到对象生命周期：初始化时取得或接管资源，析构时释放。异常沿调用关系传播时，离开作用域的已构造局部对象会按规则销毁，因此普通返回与异常路径共用析构清理，不必在每个出口重复写释放代码。它适用于内存、文件、锁和设备句柄，但前提是所有权明确且析构不让异常逃出。

**完整逻辑**：先说资源责任绑定，再按创建、抛出、栈展开、析构、进入 `catch` 的顺序说明。补充构造未完成时外层对象不析构，但已构造成员会清理；最后说明 RAII 不等于“所有操作不失败”，只是让退出路径统一可靠。

**可能连续追问**：

- RAII 只适用于动态内存吗？
- 构造函数抛异常时，当前对象会调用析构函数吗？
- 为什么析构函数通常不应抛异常？
- `unique_ptr` 怎样体现 RAII？

**容易失分的说法**：把 RAII 说成垃圾回收；说抛异常后局部对象都不析构；忽略部分构造的成员清理；把“常见放在栈上”当成 RAII 定义。

### 题 2：基本保证、强保证和不抛保证有什么区别？`noexcept` 等于不会失败吗？

**30 秒回答**：基本保证要求异常后对象仍有效且无资源泄漏，但值可能改变；强保证要求失败时对外状态保持调用前；不抛保证承诺异常不离开操作。`noexcept` 表达最后一种边界承诺，却不表示内部不会遇到失败，也不会自动捕获异常；异常若越过该边界会调用 `std::terminate`。常用策略是先完成可能失败的准备，最后一次提交状态。

**完整逻辑**：逐级说明失败后能依赖什么，再用“先改后查”和“先查后改”比较强保证。说明组合函数的等级取决于各子操作；最后区分业务失败、异常外逃和 `noexcept` 契约，避免把关键字当自动安全机制。

**可能连续追问**：

- 基本保证是否要求失败后所有值不变？
- 怎样用“先准备、后提交”实现强保证？
- 异常逃出 `noexcept` 函数后，外层 `catch` 能否正常处理？
- 为什么标准容器关心移动构造是否为 `noexcept`？

**容易失分的说法**：把三种保证说成性能等级；说强保证意味着永不失败；说 `noexcept` 会把所有 `throw` 变成编译错误；不给出失败后的状态边界。
