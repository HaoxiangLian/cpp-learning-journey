## 一、概念判断题

1. **正确。** `set` 的值类型就是键类型；`map` 的元素可看作 `pair<const Key, T>`，`first` 是键，`second` 是映射值。
2. **错误。** `set` 是唯一键容器，第二个 7 与已有 7 等价，不会形成另一个元素；最终键为 2、7，`size()` 为 2。
3. **错误。** 缺失键会被插入，映射值按值初始化；对 `int` 得到 0，容器的 `size()` 增加。
4. **错误。** 有序容器的键等价由 `!comp(a, b) && !comp(b, a)` 决定，不要求与 `a == b` 相同。
5. **错误。** 冲突只使不同键进入同一候选桶，容器仍用键相等判定区分元素；不同键可同时存在。
6. **错误。** 按键查找是平均常量、最坏线性复杂度；不良哈希分布或大量冲突会扩大候选范围。

## 二、键状态、复杂度与失效分析

1. 创建后 `counts` 为空。`find("force")` 返回 `end()`，不修改容器，所以 `missing == counts.end()` 且 `size()` 仍为 0。`counts["force"]` 第一次插入键并建立值 0，因此 `first` 为 0、`size()` 为 1。最后一行把对应值从 0 加到 2，键仍只有 `force`。
2. `12 / 10` 与 `19 / 10` 都为 1，所以两个方向比较都为 `false`，二者是容器眼中的等价键；`12 / 10 < 25 / 10` 为 `true`。最终保存第一次出现的 12 和不同组的 25，按比较器顺序为 `12, 25`，`size()` 为 2。
3. 12 与 22 的哈希值都为 2，因此位于同一桶；但 `12 == 22` 为 `false`，所以它们不是等价键。容器保存两项，`size()` 为 2，`find(22)->second` 为 `vision`。桶只缩小候选范围，键相等判断才确认目标。
4. `rehash` 后 `iterator` 失效，不能解引用、比较或移动；`reference` 与 `pointer` 仍指向现存元素的字符串，可以使用。若随后删除键 12，该元素生命周期结束，三者都不能再用于访问；“重新散列保留引用”不能扩大到删除以后。
5. 时间戳有序与范围需求选 `map`，按键查找/插入为对数复杂度且按比较器迭代；无顺序的设备 ID 去重与普通高频查询可选 `unordered_set`，平均常量、最坏线性；唯一报警等级且按级别输出选 `set`。`missing_key_order.cpp` 因 `SensorKey` 没有可用顺序关系而编译失败，修复为提供合法比较器；`stale_unordered_iterator.cpp` 可编译但在重新散列后解引用失效迭代器，属于未定义行为，修复为重新 `find`。

## 三、编程题参考实现

完整实现见 [`associative_choices.cpp`](associative_choices.cpp)。有序状态使用 `map`，报警去重使用 `set`，无顺序标签查找使用 `unordered_map`。哈希冲突通过桶接口观察，但元素身份仍由键相等判断；重新散列后只保留现存元素指针，并重新取得迭代器。

参考输出：

```text
ordered ids: 7 12 20
unique alarms: 2
same bucket: true
lookup 22: vision
pointer after rehash: force
refreshed key: 12
```

注意：若重新散列后删除键 12，保存的字符串指针也会失效；若程序需要长期跨修改保存身份，优先保存稳定业务键并在使用前重新查找，而不是让容器迭代器承担长期身份。
