# 每日讲义编写规范

本规范用于人工维护与每日自动发布。学习者按“C++ 基础薄弱、第一次系统学习”设计。目标不是把术语、代码和错误示例堆成并列栏目，而是让学习者先看懂一段代码中发生了什么，再逐步建立可复述、可验证的语言模型。

## 一、先建立可观察模型，再提高抽象层级

一个概念的首次解释必须按以下“理解阶梯”展开：

1. **代码事实**：先给 5—15 行最小代码，或一个调用/对象状态时间线。
2. **普通话结论**：不用新术语回答“现在有哪几个对象、谁被修改、什么时候创建、什么时候不能再用”。
3. **正式术语**：学习者已经看到现象后，再给中文名、英文名和唯一正式定义。
4. **逐行映射**：把定义中的每个关键部分指回代码，不让定义悬空。
5. **实现边界**：最后才说明编译器、操作系统或 ABI 可能怎样实现，以及标准没有保证什么。
6. **面试压缩**：在面试部分把前五步压缩成 30 秒回答，而不是让正文一开始就使用面试式高度概括。

“语言规则/标准语义”表示所有符合相应 C++ 标准的实现都必须保持的代码含义和行为约束；“实现方式/实现模型”表示编译器和运行环境为了满足这些规则所选择的具体做法。首次使用这些表达时必须就地写出这层意思，不能假设初学者已经理解。

`ABI`、调用帧、寄存器、优化器、自由存储、分配器、内存布局等词只能在当前代码的基本结论已经能够独立成立后出现。若删除这段进阶说明，学习者仍应能预测输出、判断对象是否有效并完成当日练习。

优先使用以下工具降低抽象度：

- “调用前 → 进入函数 → 修改后 → 返回后”的状态表；
- “标准回答什么问题 / 常见实现回答什么问题”的两列表；
- 对指针分别标出“指针对象”和“被指对象”；
- 对生命周期分别标出“创建点、最后一个合法使用点、结束点”；
- 在进阶边界前增加“初学者先记住……”的一句话结论。

禁止一上来用“语义、实现模型、物理布局”互相解释，也禁止用比喻代替对象、值、存储和生命周期的准确关系。

## 二、讲义采用“上下文内定义”，不单列术语卡

每日讲义不设置“今日术语卡”章节。新术语第一次进入核心讲解时，按下面的顺序就地出现：

1. 先提出一个学习者能观察到的实际问题。
2. 给出不冒充正式定义的直观模型。
3. 写出与当日 `glossary/dayXX.md` 完全一致的一句话正式定义，并链接对应锚点。
4. 立刻把术语映射到当前最小代码中的具体部分。
5. 说明它决定什么、不决定什么，以及标准保证与常见实现的边界。
6. 给出错误代码、错误类别、后果边界和修复方向。

[`glossary.md`](glossary.md) 只负责按天导航；每个 `glossary/dayXX.md` 保存该日首次出现术语的唯一规范定义。讲义重复同一句定义，是为了让学习者不离开当前语境也能完成推理。新增术语前必须搜索整个 `glossary/` 目录；若定义需要修正，必须同时检查当日术语文件、首次出现的讲义和面试答案，不能用另一套近义说法制造第二个定义。

发布第 XX 天时，必须同时创建 `glossary/dayXX.md` 并把索引中该日从纯文本计划路径改为可点击链接。不得提前创建未发布日期的空白术语文件；这样发布状态、讲义和术语目录始终一一对应。

## 三、核心知识使用四步结构，但写成连续叙事

每天选择 2—4 个真正需要深入理解的机制，每个机制使用以下固定骨架：

### 1. 实际问题

说明该机制解决什么真实问题。示例可以使用传感器、轨迹或任务队列，但领域背景最多承担情境作用，不能引入额外算法负担。

### 2. 概念落点

从刚刚观察到的代码状态过渡到准确术语。首次术语必须同时出现中文名、英文名、正式定义和术语表链接；随后说明它决定什么、不决定什么。不要用尚未解释的术语解释新术语，也不要把面试总结句直接当作初学者的第一次解释。

### 3. 代码与机制

先用最小代码或状态表逐行映射概念，确认学习者能够预测代码，再解释必要的编译器、对象、内存或运行时机制。必须明确区分：

- C++17 标准保证；
- 主流 GCC/Clang 或常见 ABI 的实现方式；
- 为帮助理解而使用、但不能代替定义的直观模型。

顺序不能倒置：不得先讲寄存器、ABI、优化或物理布局，再让学习者反推源代码规则。

### 4. 错误做法与修复

反例必须明确标为编译错误、链接错误、有定义但结果不符合预期、内存泄漏、悬空、未定义行为、数据竞争或死锁中的一类。不能把“可能发生”改写成“必然发生”，也不能只给错误结论而不给修复代码或修复方向。

每个机制末尾增加一个“小检查”，要求学习者用刚建立的模型解释一行代码或一个边界。它用于即时检索，不替代文末正式练习。

## 四、每日固定外层结构

每份已发布讲义必须保留：

1. `🎯 今日攻坚目标`
2. `🔁 前置知识检查`
3. `📖 核心知识重构`
4. `💻 最小可运行示例`
5. `🐛 错误代码诊断`
6. `🎤 高频面试实战`
7. `✍️ 当日练习`
8. `🧠 深度思考题`
9. `✅ 完成标准`

每日总量仍控制在 90—120 分钟，最多引入五个主要概念组。普通语法只需“准确规则 + 最小例子”，不要为了形式把每个关键字都扩写成核心机制。

“高频面试实战”在讲义中保留两道主问题的 30 秒回答、完整答题逻辑、连续追问列表和失分说法，保证当天学习上下文完整。每道连续追问的逐题参考答案统一放入 `interview/answers/dayXX.md`；学习者应先口述，再打开答案文件核对。`interview/answers/README.md` 只负责按天导航，未发布日不得提前创建空白答案文件。

## 五、资料使用顺序

资料的叙事方式和事实权威性要分开判断：

1. 语言规则优先核对 ISO C++ 标准文本或公开工作草案。公开草案不是已发布 ISO 标准本身，引用时要标明这一边界。
2. 工程建议优先参考 [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)。该指南通常把规则、理由、示例、例外和检查方式放在同一上下文中，本课程借鉴这种组织逻辑。
3. 编译器和工具行为参考 GCC、Clang、CMake 或供应商官方文档，并明确其适用范围。
4. 普通文本教程可以帮助判断初学者在哪一步容易卡住，但不能作为标准保证的唯一依据。

与第 2 天直接相关的依据：

- Core Guidelines [ES.20：始终初始化对象](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-always)、[ES.23：优先使用花括号初始化](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-list)和 [ES.25：除非对象需要改变，否则将其设为 `const`](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-const)，同时保留各自的例外与适用条件。
- C++ 公开工作草案的[列表初始化与窄化规则](https://eel.is/c++draft/dcl.init.list)，用于核对 `int value{2.0}` 为非良构程序，而不是把它仅描述成“某编译器可能警告”。
- Microsoft Learn 的 [Initializers](https://learn.microsoft.com/en-us/cpp/cpp/initializers?view=msvc-170) 可用于对照几种初始化写法；其中供应商相关内容不能扩大成所有实现的标准保证。

## 六、提交前自检

- 删除讲义中的独立“今日术语卡”后，核心叙事是否仍在首次使用处给出准确定义？
- 每个正式定义是否与当日 `glossary/dayXX.md` 一致并链接到唯一锚点？整个术语目录中是否没有同名重复条目？
- 每个机制是否都能从实际问题走到代码、边界、反例和修复？
- 正式定义之前是否已有代码事实或状态变化？学习者能否先用普通话回答“谁、变了什么、何时失效”？
- “语义、实现模型、ABI、寄存器、优化器、自由存储”等抽象词是否都在出现处得到解释，并且只承担进阶边界而非基础结论？
- 暂时遮住实现边界后，学习者是否仍能预测示例、判断错误并完成小检查？
- 正确示例是否独立通过 C++17 构建，故意错误是否被隔离？
- 面试回答是否先说条件，再给结论，并为连续追问保留标准边界？
- 当天 `interview/answers/dayXX.md` 是否与讲义中的两道主问题和全部连续追问一一对应，并已从答案索引和题库链接？
