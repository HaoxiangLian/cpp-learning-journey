## Q005

**主问题**：隐式转换和显式转换有什么区别？`static_cast` 是否代表安全？

### 30 秒回答

隐式转换由初始化、赋值、运算或调用等上下文按语言规则触发；显式转换由程序员写出转换意图，例如 `static_cast<int>(value)`。显式写法更容易审查，但不自动保证安全：浮点转整数可能丢失小数，截断后的值无法由目标整数类型表示时还会产生未定义行为，因此要先确认业务精度并检查范围。

### 完整答题逻辑

先按“谁触发转换”区分，再用 `double` 到 `int` 说明向零截断；接着说明列表初始化会拒绝某些窄化；最后给出显式转换的边界。好的回答不会把所有隐式转换判错，也不会把 `static_cast` 当成压制诊断的万能工具。

### 连续追问与参考答案

#### 追问 1：`double value{5 / 2};` 为什么不是 `2.5`？

**参考答案**：`5` 和 `2` 都是 `int`，所以 `/` 先执行整数除法，得到 `2`。随后这个结果才转换成 `double` 的 `2.0`，接收对象的类型不会倒推前面的除法重新计算。需要 `2.5` 时，应在除法前让至少一个操作数成为浮点类型，例如 `static_cast<double>(5) / 2`。

#### 追问 2：`static_cast<int>(-3.8)` 得到什么？

**参考答案**：这个值在 `int` 可表示范围内，浮点到整数转换会丢弃小数部分，也就是向零截断，因此得到 `-3`，不是向下取整得到 `-4`。回答必须保留范围条件；不能把这个结果推广到超出目标整数范围的值。

#### 追问 3：`int value{3.5};` 为什么与 `int value = 3.5;` 的诊断不同？

**参考答案**：花括号执行列表初始化，并应用窄化检查；浮点到整数属于被禁止的窄化，所以 `int value{3.5};` 非良构，必须诊断。`int value = 3.5;` 使用另一种初始化形式，允许相应隐式转换，通常得到 `3`；编译器可能警告，但语言规则不要求把它拒绝为错误。

#### 追问 4：浮点值超出 `int` 范围时能否依赖某个固定结果？

**参考答案**：不能。如果截断后的值无法由目标整数类型表示，浮点到整数转换会触发未定义行为；NaN 也不能提供可依赖的整数结果。不能声称一定饱和到 `INT_MAX`、一定回绕或一定崩溃。工程上应在转换前用符合业务和类型范围的条件检查。

### 容易失分

- 说显式转换一定安全。
- 认为接收者是 `double` 就会把此前的整数除法变成浮点除法。
- 把越界转换说成必然得到最大整数、回绕或崩溃。

## Q006

**主问题**：`&&` 和 `||` 的短路规则是什么？它怎样影响代码正确性？

### 30 秒回答

内置 `&&` 和 `||` 从左操作数开始求值。`&&` 左侧为假时不求值右侧，`||` 左侧为真时不求值右侧。它们不仅组合真假，还能让左侧建立右侧的前置条件，例如先检查除数不为零；交换左右条件可能改变右侧是否执行，从而改变程序正确性。

### 完整答题逻辑

先分别说清两个停止条件，再给 `count != 0 && total / count > 2`。左侧为假时，整数除法不会执行。最后说明这一顺序保证来自内置 `&&` 和 `||` 的具体规则，不能泛化为所有运算符都按同样方式从左到右求值。

### 连续追问与参考答案

#### 追问 1：`false && function()` 是否调用函数？

**参考答案**：对内置 `&&`，不会。左操作数已经是 `false`，整个表达式不可能为真，因此右操作数 `function()` 不求值。若函数具有输出或修改状态等效果，这些效果也不会发生。

#### 追问 2：`true || function()` 是否调用函数？

**参考答案**：对内置 `||`，不会。左操作数已经为 `true`，整个表达式结果已经确定，右操作数不求值。不要把这一规则误记成“`||` 左侧为假时短路”；左侧为假时仍需检查右侧。

#### 追问 3：为什么交换两个看似等价的条件可能引入除零？

**参考答案**：`count != 0 && total / count > 2` 先检查前置条件；当 `count` 为零时，右侧不执行。交换为 `total / count > 2 && count != 0` 后，整数除法位于左侧，必须先求值，零除会在保护检查之前触发未定义行为。逻辑真值在理想数学中可能看似等价，求值过程却不同。

#### 追问 4：`if (ready = true)` 是什么错误，是否一定编译失败？

**参考答案**：这是把赋值表达式写进条件。它把 `ready` 改为 `true`，赋值表达式结果也为真，所以分支会进入；行为有定义，但通常不符合意图。编译器可能警告，本课程的 `-Werror` 可能让构建失败，但 C++ 语言本身不要求它必然是编译错误。检查布尔状态时直接写 `if (ready)`。

#### 追问 5：`switch` 忘记 `break` 是否属于未定义行为？

**参考答案**：不属于。控制会继续执行后续 `case` 标签下的语句，这是有定义的贯穿行为，但经常造成非预期结果。确实需要贯穿时，可在 C++17 中使用 `[[fallthrough]]` 表达意图；不需要时应写 `break` 或重构分支。

### 容易失分

- 说右侧会先算完再被丢弃。
- 把短路保证扩大到所有逻辑相似的表达式或所有运算符。
- 把条件中的赋值或 `switch` 贯穿直接说成未定义行为。
