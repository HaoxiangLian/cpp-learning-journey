## Q001

**主问题**：编译错误和链接错误有什么区别？

### 30 秒回答

编译错误发生在某个源文件被翻译和检查时，例如语法错误、名称不可见或类型不匹配。链接错误发生在分别翻译的结果被组合时，例如调用处已有声明，但对应定义没有参与链接。主流工具链常分别报告两类错误，但 C++ 标准不强制 `.o` 文件或独立链接器进程。

### 完整答题逻辑

先按阶段分类，再举最小例子，最后给排查方向。缺少分号时，单个源文件无法完成翻译，属于编译错误；`main.cpp` 已看到 `int status_code();`，却没有相符定义参与完整程序构建时，调用点可以通过编译，但组合阶段通常报告链接错误。排查编译错误先看第一条诊断及其上下文；排查链接错误先核对名称和类型是否一致、实现文件或库是否进入目标，以及工具链配置是否正确。

### 连续追问与参考答案

#### 追问 1：为什么只有声明时调用仍可能通过编译？

**参考答案**：普通函数调用的编译检查需要知道名称、参数类型和返回类型。相符声明已经提供这些信息，因此当前翻译单元可以检查调用是否合法。函数体可以位于另一个翻译单元；完整程序随后仍必须满足定义规则。声明足以通过当前编译，不等于整个程序已经拥有实现。

#### 追问 2：“undefined reference”一定是没有写实现吗？也可能是签名不一致或库顺序/配置问题吗？

**参考答案**：不一定。可能确实缺少定义，也可能是声明与定义的名称或参数类型不一致，导致它们表示不同函数；实现源文件可能没有加入目标，库可能没有被正确链接，或者 C 与 C++ 的链接约定、条件编译及特定工具链的库顺序配置不一致。应先读取诊断中的完整符号，再对照声明、定义和构建配置。

#### 追问 3：C++ 标准是否规定必须生成目标文件？

**参考答案**：不规定。标准描述源文件如何被翻译以及程序需要满足的语义规则，但不要求中间产物必须叫 `.o`、`.obj`，也不要求存在一个独立链接器进程。目标文件和链接器是主流实现模型，回答时应明确这是工程实现而非语言标准强制。

### 容易失分

- 把所有构建失败都叫作编译错误。
- 声称链接错误只可能来自“忘记写函数体”。
- 把 `.o`、符号表或独立链接器说成 C++ 标准规定。

## Q002

**主问题**：声明和定义是什么关系？

### 30 秒回答

声明引入或重新引入名称，并给出引用该实体所需的信息；定义是一种声明，还提供该实体所需的完整定义，例如函数体。不是每个声明都是定义，但定义也是声明。普通函数调用在编译时可以只看到声明，完整程序仍需满足相应定义规则。

### 完整答题逻辑

先说包含关系，再比较 `int f();` 与 `int f() { return 1; }`。前者声明函数的名称、参数和返回类型，后者同时给出函数体，所以是定义。工程中常把声明放入头文件、定义放入源文件，但这只是常用组织方式；二者必须描述同一个实体，完整程序还要遵守单一定义规则及其例外。

### 连续追问与参考答案

#### 追问 1：变量声明和函数声明是否完全相同？

**参考答案**：它们都属于声明体系，但“何时同时是定义”的规则不同。`extern int count;` 通常只声明一个在别处定义的对象；命名空间作用域的 `int count;` 则是对象定义。`int f();` 是无函数体的函数声明，`int f() { return 1; }` 是函数定义。不能用“是否出现分号”或“是否分配空间”概括所有情况。

#### 追问 2：为什么头文件中可以定义某些 `inline` 函数？

**参考答案**：`inline` 函数适用单一定义规则的特殊允许条件：它可以在多个翻译单元中出现定义，但各定义必须满足一致性等要求，并共同表示同一个实体。把定义放在头文件能让每个使用它的翻译单元看到定义。`inline` 关键字不保证编译器一定执行机器码层面的内联展开。

#### 追问 3：重复定义为什么有时链接失败、有时涉及更复杂的规则？

**参考答案**：普通具有外部链接的非 `inline` 实体通常只能在整个程序中有一个定义，重复定义常被链接器诊断。`inline` 函数、模板以及 C++17 的 `inline` 变量等存在受条件约束的多翻译单元定义规则。某些违反单一定义规则的程序不保证一定得到诊断，因此不能把“链接器没报错”当作程序合法的证明。

### 容易失分

- 说“声明永远不分配空间，定义永远分配空间”。
- 把声明和定义说成互斥概念。
- 认为 `inline` 等同于强制内联优化，或认为任意重复定义都合法。
